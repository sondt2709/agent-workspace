Phase 1 is one person, their own devices, Claude Code and no cloud account. This document gives the phase 1 parts of `architecture.md` in build detail. Phase 1 uses the final data model, module boundaries and interfaces. Phase 2 adds parts (section 12). The verification on 2026-11-22 used a local Mac, a Linux remote device and an Android 14 emulator.

## 1. Scope
Scope: all P1 requirements of `prd.md` 10.

## 2. Components
1. **awd, `aw` CLI, MCP server and skill**: TypeScript on Node.js 24, a user service on each computer, the local API on `~/.aw/run/awd.sock`, the MCP server on `127.0.0.1` (9.8).
2. **Plugins** (interfaces of `architecture.md` 6): `agent-claude` (terminal mode), `host-tmux` (default), `host-orca` (optional per device, 9.9), `host-pty` (later), `sync-syncthing` (engine supervisor and REST client), `kb-files`, `live-direct` (`wss://` on LAN and Tailscale; a placeholder package now), `push-webpush` (VAPID, RFC 8291), `link-github` (later).
3. **Desktop app**: Electron with a React + MUI renderer, the window of the local awd (10). **Android app**: Kotlin Multiplatform and Compose Material 3, own engine, Kotlin REST client.
4. **Session hosts**: phase 1 ships and tests both. `host-tmux` runs in CI e2e. `host-orca` has contract tests from recorded CLI output in CI and real runs with `AW_E2E_ORCA=1` in the release check on a real device.

## 3. Data layout
### 3.1 Folders
```
~/AW/<workspace>/                      app-private storage on the phone
├── tasks/                             Syncthing folder "tasks": all devices
│   ├── workspace.yaml                 shared file
│   ├── log/<device>.jsonl             workspace events: queue order, Inbox actions, slot leases, credential names, project removals
│   ├── schemas/<type>.v<major>.schema.json   copies of the generated schemas (awd writes them at init and start)
│   ├── devices/<device>/
│   │   ├── device.yaml                signed device record (writer: a device with the master key)
│   │   ├── heartbeat/<date>.jsonl     presence, 1 line per 30 s, UTC date; kept 7 days (writer: that device)
│   │   ├── health.yaml                writer: that device, at most once per 60 s
│   │   ├── bindings.yaml              checkouts, test slots, Use Orca, plugins and skills, "may run" (writer: that device; `aw binding`)
│   │   ├── push.yaml                  phone only: push endpoints
│   │   └── sealed/<id>.age            phone only: credential values sealed to all paired computers (10.2)
│   ├── projects/<project>/project.yaml   shared file: links, main repo, device list, default agent, test server names, switches, archived, added_at (6.9)
│   └── <task-id>/                     the internal id, never the key AW-7
│       ├── task.yaml                  snapshot (writer: the owner device)
│       ├── log/<device>.jsonl         events (writer: that device)
│       ├── approach/v<n>.md           each version written once by the session device
│       ├── artifacts/<device>/…       files (writer: that device; the phone fetches on request)
│       └── terminal/<device>.txt      screen snapshot of a tmux session: at most once per 30 s, and at each gate (3.1.1)
├── knowledge/                         Syncthing folder "knowledge": all devices
│   ├── shared/…  projects/<project>/…   Markdown, shared files
│   └── log/<device>.jsonl             knowledge change events
└── secure/                            Syncthing folder "secure": local and remote only
    ├── test-servers.yaml              shared file
    ├── credentials/<name>.age         encrypted with the workspace credential key
    └── keys/<device>.age              the workspace credential key, sealed to the device key of one computer

~/.aw/                                 never synced, mode 0700: config.yaml identity.yaml keys/ records/ pairing/ index/ logs/ history/<workspace>/ journal/ sessions/ spool/ run/ (0700, awd.sock 0600) versions/
├── sync/                              engine home: config.xml, certificate, database
├── sync-versions/<folder id>/         Syncthing "simple" file versioning, outside the AW folder
├── engine/syncthing                   the sync engine binary (`aw engine install`; `AW_SYNC_ENGINE` replaces it)
├── worktrees/aw-<key>/                the git worktree of a tmux session (9.1); an older one is named <task-id>
├── backups/claude-<stamp>.json        backups of the Claude Code state file before a trust write (0600, the last 5 stay)
└── push/<workspace id>.json           the sent pushes of this computer (0600, section 8)
```
`~/.aw/history/<workspace id>/` holds the knowledge versions (`<sha256>`, mode 0600, folder 0700) and `seen.json`, the last hash of each knowledge path that this device saw (section 5). `~/.aw/config.yaml` holds this device (slug, name, role), the registered workspace folders and `sync.community`. At the first start awd proposes a slug from the host name and registers no workspace: the first setup step makes one (`aw workspace init` with no path, or the desktop button, gives "Personal" at `~/AW/Personal`), or `aw pair` (or "Join with a pairing code" on the first screen of the desktop app) joins the workspace of another device. A new workspace makes the master key, so a device that will join must not create one first. The workspace folder rule (`docs/decisions/2026-11-24-workspace-folder.md`): the person chooses a location for each workspace (`aw workspace init --in <folder>`, `aw pair --in <folder>`, the Location field of the desktop dialogs; default `~/AW`). The location can hold other files. AW uses `<location>/<name>`, or `<name>-aw1`, `-aw2` up to `-aw99` when that name is a file, a symbolic link, a folder with other files or the folder of another workspace, and the reply names the folder that AW used. A path argument (`aw workspace init <path>`, `aw pair --path`) stays the workspace folder itself. A location of `aw workspace init --in` (or "Add a workspace") that has `tasks/workspace.yaml` is registered as that workspace. Each form refuses a folder in AW_HOME, in another workspace folder (registered or not), in the folder of an open join or in a checkout of this device (or a folder that holds one of them), and a folder that AW cannot write; symbolic links are resolved for these checks. A join chooses and reserves its folder in the init queue, so a join and an init never get the same folder. The folder stays in `config.yaml`: awd does not sync it. `aw workspace remove` unregisters a workspace on this device and keeps its files; pairing sets the slug and the role from the signed record. `~/.aw/identity.yaml` (0600) holds the user id and the master public key. The keystore holds the device key and, on the local device, the recovery phrase: the macOS Keychain (`AW_KEYSTORE=os`, the default on macOS with the default state folder), else `~/.aw/keys/<name>` (0600, folder 0700). `~/.aw/keys/device` also selects the file keystore: a LaunchDaemon has no login Keychain, so `aw service move-keys` moves the keys there before `sudo aw service install --headless`, and the LaunchDaemon sets `AW_KEYSTORE=file`. `~/.aw/records/<workspace>.json` keeps the signed records of a pairing reply until the `tasks` folder syncs. `~/.aw/pairing/<nonce>/` is the folder of an open pairing. `AW_HOME` replaces `~/.aw` (tests). Each awd removes its own heartbeat files older than 7 days; that removal is not a Sync problem.

**3.1.1 Terminal snapshot.** The session device writes `terminal/<device>.txt` for a running tmux session: at a watchdog check (every 30 s) when the screen hash changed and the last write is 30 s old, and at once after each `gate.opened`. The first line is a JSON header `{"kind":"aw-terminal","v":1,"device","session","host","socket","window","captured_at"}` (`captured_at` from the clock module, form `2026-11-23T14:20:05.000Z`); the next lines are the visible screen (`capture-pane -p -J`). The writer redacts the full screen first, also a value that a TUI wraps over 2 to 8 screen lines (those lines become one redacted line), then keeps the last 200 lines and at most 64 KiB, cut at a line start. AW writes no snapshot of an Orca session. A reader reads only regular files named `<device slug>.txt` (no link, conflict copy or temp file) and shows the newest by `captured_at`; a file with no valid header (each key, `socket` null or `[A-Za-z0-9_-]{1,64}`) is text with no time (`contracts/fixtures/terminal/cases.json`). The person route `GET /v1/workspaces/{ws}/tasks/{task}/terminal` and `aw terminal <task>` give it with the targets of "Open the terminal" and "Sign in".

The folder ids are `aw-<workspace id>-tasks`, `-knowledge` and `-secure`. Other documents write `workspace.yaml`, `log/`, `devices/` and `projects/` without the prefix `tasks/`. A task folder has the internal id as its name, because 2 offline devices can take the same key. The ready check waits only for `knowledge` and `secure`, because `tasks` is rarely at 100 % while agents write logs.

### 3.2 Documents
A document is one YAML file with a `kind` and a schema version. Example snapshot:
```yaml
kind: task
schema: 1
id: 0193a7c2-5b1e-7c3a-9f20-6d1e2a4b8c01   # folder name
key: AW-7                                   # display alias (3.6)
project: billing-api
title: Fix the flaky invoice test
first_message: "/opsx:explore The invoice test fails 1 time in 5 on CI."   # raw text, passed as is
stage: implement            # backlog, discuss, ready, implement, review, done
needs_you: []               # open gate ids: the "Needs you" lane
paused: null                # {cause, since, resumes_at, next_step, needs_human}
assignee: claude@ubuntu-01
claim: {epoch: 3, device: ubuntu-01, session: 0193a7d1-…}   # 9.6
approach: {latest: 2, confirmed: 2}        # approach/v2.md
ready: {passed_on: ubuntu-01, missing: []}
test_server: billing-k3d    # a name in secure/test-servers.yaml
credentials: [stripe-test]  # names only, never values
parent: null
subtasks: [0193a7e0-…]
depends_on: []
links: ["github:acme/billing-api#412"]
branch: aw/AW-7             # checkpoint branch, fixed at the first session
includes: {macbook-pro: 41, ubuntu-01: 118, pixel-9: 6}   # log lines in this snapshot
```
1. Write a YAML file to `<name>.aw-tmp`, then rename it. The ignore pattern `*.aw-tmp` keeps the temp file out of sync.
2. The description is a view, not a field. AW builds it from the first message, the confirmed approach, the test server name, the links and the subtasks. It never shows a credential.
3. The phone has no `secure` folder. It reads the test server names from `project.yaml` and the credential names from the workspace logs.
4. Front matter in each knowledge file holds the apply mode, the lock and the provenance: `apply` (`always`, `auto`, `files`, `manual`; default `always` in `rules/` of a scope, else `auto`), `description`, `globs`, `locked`, `source` (for example `claude@ubuntu-01 on AW-7`), `author`, `task`, `learned_at`, `validated_at`. Unknown fields stay. A bad front matter gives the defaults and a warning.

### 3.3 Logs
```json
{"v":1,"id":"0193a7d0-…","hlc":"2026-11-22T14:20:01.123Z#0000","dev":"ubuntu-01","type":"gate.opened","by":"claude@ubuntu-01","data":{"gate":"0193a7d0-…","kind":"confirm_approach","version":2}}
{"v":1,"id":"0193a7d4-…","hlc":"2026-11-22T14:21:40.002Z#0000","dev":"pixel-9","type":"gate.answered","by":"human@pixel-9","data":{"gate":"0193a7d0-…","version":2,"answer":"confirm"}}
```
1. Each device appends only to its own log files. It never rewrites a line.
2. awd buffers log lines and writes each file at most once per second. A gate, a stage change or a human action is written at once. A targeted scan follows each write (6.3).
3. A line is at most 64 KiB. Larger content goes to `artifacts/`. A reader (awd and the phone) reports a line nested deeper than 64 levels of objects and arrays as a bad line.
4. **Thread (principle 8).** The session device writes each message as raw text, never as a summary: `message.human` from the UserPromptSubmit hook (`source`: `first`, `typed`, `answer`, `phone`; `delivery_id`) and `message.agent` from the Stop hook. A sending device writes only `gate.answered` or `message.sent {id, text, to_session}` to its own log, so each text is in the thread once (`workflow.md` 4.3). The gate, approach and result events complete the thread.
5. **Redaction.** Each event writer replaces each credential value of the session with `[redacted:<name>]` before it writes a line, and each session token with `[redacted:mcp-token]`. It checks the plain, base64 and URL-encoded forms. This covers hook payloads, agent replies and terminal snapshots. The files layer also redacts each text file of a task before it writes it: the terminal snapshot, the approach versions and the artifacts (the long message file `text-<id>.md`, `aw artifact add`, the result, the result artifacts, the handoff). A file is text when it is strict UTF-8 with no NUL byte; a terminal snapshot is always text (its bytes are decoded with replacement characters). A file with no NUL byte but a byte that is not UTF-8 (a Latin-1 byte in a log), and a UTF-16 file (a byte order mark, or NUL bytes at only odd or only even offsets), are redacted in their bytes; the other bytes stay. AW writes a binary file (each other file with a NUL byte) as it is, so a value inside a binary artifact stays. Each writer that shortens agent or screen text (a message preview, a gate title or text, a tool summary, the last terminal line, a snapshot) redacts the full text first and cuts it after, so a value across the cut keeps no prefix. `artifact.added` has the size and the sha256 of the written bytes.

### 3.4 Schemas
1. zod schemas in `shared/schema` are the one source. `pnpm schema:generate` writes `contracts/schemas/<type>.v<major>.schema.json`, the schema samples for the Kotlin tests in `contracts/samples/schema-samples.json` and the Kotlin data classes in `android/shared/generated/kotlin/` (from the JSON Schemas; `android/shared` compiles them). A check that a pattern cannot express (a real HLC date, a relative path) is the JSON Schema annotation `x-aw-check`. CI fails on drift.
2. A new optional field is a minor change. A removed or renamed field is a major change, with a new file `<type>.v<major+1>.schema.json`. awd and the phone read the current and the previous major, and validate each file on read.
3. All field names in documents and events are snake_case. Objects accept unknown fields, so an older device keeps the fields of a newer minor version.
4. A document has `kind` and `schema` (its major version). An event has `v`, the major version of its event type. An event of an unknown type is kept and not applied: a new event type is a minor change.

### 3.5 Local index
1. One SQLite file per workspace, `~/.aw/index/<workspace id>.sqlite` (`node:sqlite`), and a Room database on the phone. Never synced. Tables: files (path, lines, errors), documents (kind, path, JSON), events (task, HLC, device, type, applied, reason, JSON; no heartbeats), tasks, projects, devices, queues, slots, credentials, issues, presence. Each table keeps the JSON of the merged view, with the simple fields as columns. The Room index of the phone (`android/shared`, Room 3, `databases/index-<workspace id>.sqlite` in the private folder of the app) has the tables tasks, events, issues, documents, projects, devices and presence, and the queries "Needs you", tasks by project and stage, and the thread of a task by HLC; the JVM tests run the same database with the bundled SQLite driver.
2. awd parses each changed file (from the watcher and the engine events) and updates the index. The merge reads only the new bytes of a log that grew. A log that became shorter, was replaced or was removed makes it read all files again. A full read gives the same rows as the incremental path. A command `aw index rebuild` comes in a later phase. Queries use the MongoDB query syntax: awd translates exact conditions on the columns to SQL and applies `sift` to the rows. The phone uses fixed Room queries; the tested subset of the syntax for saved filters comes with the android-ui task.
3. The merge cases in `contracts/fixtures/merge/` each have an expected view. awd and the phone must give the same view (`engineering-rules.md` 7.4.15).

### 3.6 Ids, clocks and task keys
1. Ids are UUIDv7. A device slug (`ubuntu-01`) is fixed at pairing and unique in the device list. The HLC is `<UTC time, ISO 8601 with ms>#<4-digit counter>`. It sorts as text, and the device slug breaks ties. The event id breaks a tie of the same HLC and device, which only a broken device can make.
2. Task keys follow `architecture.md` 4.3.3: the next number that the device knows; priority on a collision; `task.rekeyed` by the other device. Folders, tmux window names and links use the id. `aw` commands accept the key and the id.
3. **HLC bound.** The merge holds back an event whose HLC is more than 24 h ahead of the local clock. It reports the event as `future_hlc` and merges it when the local clock comes within 24 h. So one bad line cannot move the HLC of each device far forward.

## 4. Ownership rules
`architecture.md` 4.3.1 is the table. awd enforces it:
1. The `files` module refuses a write to a file that this device does not own. A reader rejects an event in `log/<d>.jsonl` whose `dev` is not `d`, and reports "Sync problem".
2. The merge applies a state event only when its device owns the task at that point in the HLC order.
3. The owner device of a task is the device with the highest `task.claimed` epoch (9.6). Before the first claim, the creating device writes the snapshot.
4. **First assignment.** A task with no assignee, from a human or an agent, opens the gate "Assign task" ("Needs you: assign"). AW never assigns it alone. The only exception is the project switch "Assign new subtasks to the default device" (off by default) (task-model decision §5.1).
5. The highest-priority online device resolves conflicts in shared files (6.6).

## 5. Knowledge history
1. A knowledge change has 3 sources: `aw learn` and `aw kb` through awd, a human edit that the watcher finds, and a file that sync replaced or deleted.
2. **Copy before write.** Before awd writes a knowledge file, it stores the current content in `~/.aw/history/<workspace>/<sha256>`. The watcher stores each human edit the same way. Then awd appends `{path, hash, base, author, task, kind}` to `knowledge/log/<device>.jsonl`. A sync change is logged by its author device. Other devices only store the version.
3. **Syncthing versioning.** "Simple" versioning, with its folder `~/.aw/sync-versions/<folder id>` outside the AW folder, keeps each version that another device changed or deleted. It never keeps an edit of the device itself, so item 2 is necessary. In the verification, "staggered" mode lost a version.
4. History of a file = the change events for its path from all devices, in HLC order, each with the author, the task, the time and a diff from its base. A conflict shows as `replaced` with Undo.
5. Undo writes the base content as a new change of kind `undo`, then a targeted scan. The other device had the restored file 1.4 s later. On the phone, Undo is a request event (`architecture.md` 4.8.2).
6. At pairing, a new computer copies the history store from a paired computer through the pairing folder (section 7). The phone reads the history from a computer. A later phase adds `aw kb export --git <path>`: it writes a git repository outside the AW folder (`architecture.md` 4.8).
7. **Direct edits and sync changes.** At the start, after each watcher batch and after each remote change that the sync engine reports in `knowledge/`, awd compares each knowledge file with `seen.json`, and stores each new version. A new hash is a sync change when the newest change event of the path has it, or when an event of another device changed the path from the seen hash to it. Else, after 2 s (the log line can arrive after the file), awd logs it as an `edit` or a `delete` by `human@<device>`. A credential value in a direct edit is written back redacted, and only the redacted version is stored and logged.
8. **Suggestions.** An agent change to a rule, a file with `apply: always` (current or new), a locked file or shared knowledge (or knowledge from another person) is not written. awd appends `knowledge.suggested` with the redacted content (at most 48 KiB) and the reasons. A human accepts it (awd applies it, with the suggestion id in `knowledge.changed`, then appends `knowledge.suggestion_resolved`) or rejects it. The first resolution in merge order wins; an applied change makes it accepted. The gate "Approve knowledge change" shows this record (task-loop).
9. **Learned items and context.** `aw learn <task> --file --title` writes `projects/<project>/learned/<date>-<slug>.md` with the provenance. `aw kb context <task>` gives the session context: "Read now" (rules, `always`, a `manual` file named in the task, a `files` file whose glob matches a task path) within 40,000 characters, then the `auto` and `files` lists. A dropped file gets a warning. The text is at most 9,000 characters, a list and a short header; the agent reads the files itself. A task path is a path that the title, the first message or the confirmed approach names (a token with a `/` or a file extension, not a URL), or a file that the session worktree changed (`git status`, and `git diff --name-only` from the HEAD of the checkout). `aw learn <task> --nothing-new` records "Nothing new". Each learning step writes `task.learned` (`path` and `change` for a learned item) to the task log (openspec agent-learning).
10. **Agent callers.** awd takes the identity of an agent only from the session token (`Authorization: Bearer <token>`). Inside a session, the CLI and the hooks send `AW_MCP_TOKEN`. The person routes of the local API (workspace init, rename and remove, project add, edit and remove, the bindings of this device, task create, edit, assign, archive, message to a session, gate answer, session stop, the agent queues, the sync writes, `kb accept|reject`, and each identity, device, pairing and credential route, also the reads of the recovery phrase and of a credential value) refuse a session caller with 403 `refused`. An agent gets a credential only through the session start. A caller with no token is the person, except when awd finds that the peer process of the socket connection is in the process tree of a running session: then it is that session (macOS `lsof`, Linux `ss`, then the parent chain from `ps`; only for a person route or a knowledge write, and only while a session runs). A write to `shared/` or to a rule (the folder `rules/` in any letter case) is refused for a session caller: only a person approves or changes them. A session caller writes only the knowledge of the project of its task. A write of another file of that project and an Undo have the agent as author, so the approval rules apply. `aw learn` has the agent as author and must name the task of the session. An unknown or revoked token gets 401 `unauthorized`.

## 6. Built-in sync
### 6.1 Engine on computers
AW bundles the official, unmodified Syncthing binary (v2.1.7 at the time of writing, `tech-stack.md`). CI checks its sha256 and the PGP signature. The installer ships `THIRD_PARTY_NOTICES` with the MPL-2.0 text, the authors and a link to the source tag. The engine is never visible to the user.

At the first start, awd does these steps:
1. Run `syncthing generate --home ~/.aw/sync --no-port-probing`.
2. Write `config.xml` from the template of 6.2: global discovery, relays, NAT traversal and usage reports off. The engine never runs before this step. In the verification, a start with the default config used public discovery and opened router ports within 33 s.
3. Run `syncthing serve --home ~/.aw/sync --no-browser --no-upgrade --no-restart`. Wait for `GET /rest/system/ping`. Make each later change through REST, for example global discovery and relays when the switch of 6.2 is on.

At each later start, awd runs step 3 only, when `config.xml` is the AW config: REST on `~/.aw/run/sync.sock`, an API key, and NAT, usage reports, crash reports and upgrades off. Else (for example awd stopped between step 1 and step 2, and the config of `generate` has the GUI on TCP 8384 with NAT and reports on) awd runs steps 1 to 3 again; `generate` keeps the certificate, so the device id stays. When awd cannot prepare the engine home (`generate` fails, or `~/.aw/run/sync.sock` is longer than 103 bytes), the engine state is `failed`, the log has the cause, and awd tries again with the backoff. awd does not wait for the engine: `/readyz` and the heartbeat do not depend on it. awd supervises the engine: a health check with `/rest/system/ping` every 10 s, a restart with backoff (1 s to 60 s), a stop before an AW update. Syncthing v2.1.7 runs as 2 processes, a monitor and a worker child, also with `--no-restart`; when the worker dies, the monitor exits. awd records both pids in `~/.aw/sync/aw-engine.pid`, checks both, sends each stop signal to both (ST10), and at start stops an engine that an earlier awd left: only a `syncthing` process with `--home=~/.aw/sync` in its arguments, so an old pid that is now the user's own Syncthing stays. A failed config step after a start (a REST call for the options, devices, folders or ignores) does not stop the engine; awd tries it again at the next health check. The device id of this device comes from the engine certificate (`syncthing device-id`) and `/rest/system/status`, never from the `config.xml` text: the engine writes the folder devices and the peers there, sorted by id.

awd finds the engine at `AW_SYNC_ENGINE` or `~/.aw/engine/syncthing`. `aw engine install` puts the pinned release binary there: it downloads the archive of the platform (or reads `--archive <file>`) and refuses an archive with another sha256. `aw service install` runs it first, prints the install command of tmux when tmux is missing, and restarts awd when the engine is new. With no binary, awd runs with sync off and `/readyz` reports `sync_engine: not_installed`; `aw doctor` names the fix. awd checks for the binary every 5 s and starts the engine when `aw engine install` placed it, with no restart. The engine log is `~/.aw/logs/sync-engine.log` (10 MB, 3 old files). `aw sync status|now|pause|resume` and `aw sync peer add|remove` call the local API `/v1/sync`. `aw sync peer add` (`POST /v1/sync/peers`) shares each folder, `secure` too, with a device id that has no signed device record. It is a test path only: awd refuses it (403 `refused`) unless `AW_SYNC_TEST_PEERS=on`, and the peer stays in memory until the next awd start. awd gives the engine the peers of the signed device records (section 7). A pause lasts until `aw sync resume` or the next awd start: Syncthing v2.1.7 keeps `POST /rest/system/pause` in memory only, and awd shows `paused: false` after a restart. A peer added during a pause is paused too.

### 6.2 Engine settings
| Setting | Value | Reason |
|---|---|---|
| Home, ports, name | `~/.aw/sync`, own listen port (`AW_SYNC_LISTEN`, default `tcp://0.0.0.0:22300`, TCP only), the AW device slug as the name | A Syncthing that the user already runs stays unchanged. No OS hostname. |
| GUI and REST | The Unix socket `~/.aw/run/sync.sock` (mode 0600; the path must be shorter than 104 bytes), random API key in `config.xml` (mode 0600) | Only awd talks to the engine. No web GUI for the user. The engine keeps the key in plain text in `config.xml` anyway, and a keystore needs a session bus on a headless Linux device. |
| Discovery, relays | Off at the first start. Then local discovery on; global discovery and relays follow the switch "Use community discovery and relay servers": `sync.community` in `~/.aw/config.yaml` (on by default), set with the desktop Settings or `aw sync community on\|off` (`GET/PUT /v1/sync/settings`). awd applies a change to the running engine through REST. `AW_SYNC_COMMUNITY`, when set, wins, and the switch is read-only. | Decision D18. No third-party traffic before awd reads the switch. |
| NAT traversal | Off | No port opens on the router (`prd.md` RMT-07). |
| Usage reports, crash reports, auto-upgrade | Off (`urAccepted -1`, `autoUpgradeIntervalH 0`) | No data to third parties. AW ships the engine updates. |
| Conflicts | `maxConflicts 10` | With 0, Syncthing deletes the older edit and makes no copy (6.6). |
| Reconnect interval | 5 s during pairing, after `aw sync resume` until each peer is connected (at most 10 min), and while the phone app is open. Else 60 s on computers, 20 s on the phone. | A re-pair took up to 56 s at 60 s, and at most 5.1 s at 5 s (n=3). |
| Folders | `tasks` and `knowledge` with all devices, `secure` with computers only. Send and receive, `fsWatcherDelayS 1`. | Completion per folder. No secrets on the phone. |
| File versioning | Simple, keep 10, folder `~/.aw/sync-versions/<folder id>`, on computers | Undo for changes of other devices (5.3). |
| Devices | From the valid, not revoked signed device records of each workspace (the record addresses and `dynamic`), full mesh, introducer off, auto-accept off. awd removes each other engine device, except a device of an open pairing. | ST13. |
| Ignore patterns (all) | `*.aw-tmp` | Set through REST on each device, because ignores do not sync. |
| Ignore patterns (phone) | Also `/*/artifacts` in `tasks` | Artifacts on request. |

Each folder-config change restarts the folder (ST2), so awd changes the folder config only at pairing and revoke.

### 6.3 Writes and scans
1. After each own write, also after each log flush, awd calls `POST /rest/db/scan?folder=<id>&sub=<path>`. The other device then sees the change in about 1.3 s on a LAN, against a p50 of 2.1–2.4 s without the scan.
2. A busy log file can lag up to 8 s. Other devices add 8 s before they show "No recent update" (9.6).
3. The index updates from the file watcher, never from the engine completion values, because they lag behind the files (ST4).

### 6.4 Sync now and sync before sleep
"Sync now" on the desktop (the "Sync" button of Devices and the menu bar item "Sync now") or the phone. It only syncs and shows the result; it suggests no move (`decisions/2026-11-23-manual-move.md`):
1. Always start with `POST /rest/db/scan` for each folder. Without the scan, the completion showed 100 % while the peer did not have the file. The scans use the time that is left of the timeout; a folder whose scan fails (for example its path is missing) is logged, and Sync now goes on. The phone also starts the engine when it does not run (6.7).
2. For each peer, poll `GET /rest/db/completion?folder=<id>&device=<peer>` and `GET /rest/system/connections`.
3. A peer is synced when it is connected, `needItems` is 0 and `remoteState` is `valid`. Never use the total completion (ST8).
4. Stop after 20 s on a computer, 60 s on the phone. Show "Synced 2 s ago", or "3 changes not synced to ubuntu-01 (offline)". The time counts from the last FolderCompletion event with 0 items of the peer (the moment it got the last change), not from the last status poll. Measured: 1.6 s for 1 file, 3.7 s for 200 files.

Sync before sleep: the desktop app listens for `powerMonitor` `suspend`, and on Linux awd holds a logind delay inhibitor. Then awd runs "Sync now" with a timeout of 5 s, best effort on macOS. The menu bar always shows the count of changes that are not synced.

### 6.5 Sync state
1. awd reads `GET /rest/events` with a long poll: StateChanged, FolderSummary, FolderCompletion, DeviceConnected, DeviceDisconnected, DevicePaused, DeviceResumed, FolderErrors, PendingDevicesChanged. It skips the Item events (ST9). Event ids start again at 1 after an engine restart, so awd then resets `since` and reads the full status.
2. Each peer shows: connected or last seen, the route (LAN, Tailscale from the 100.64.0.0/10 address, community relay from the connection type), `needItems`, `needBytes`, errors. "Synced" shows only for `remoteState` `valid` and `needItems` 0.
3. The connection state is not presence. A frozen laptop showed as connected for 2 min. Presence comes from heartbeats (9.6).

### 6.6 Conflict copies and schema errors
1. The watcher finds each `*.sync-conflict-*` file. AW never ignores one (ST5). A conflict copy of a device-owned log: the owner merges the lines by event id and removes the copy. A conflict copy of a snapshot or another file that the device owns: the owner keeps the version that its journal has (else the original, and AW rebuilds a snapshot from the logs), removes the copy and stores the other version in the history store.
2. A conflict copy of a shared file holds the older content. Its name ends with the short id of the device whose version won, not of the device that wrote the copy.
3. The resolver is the highest-priority online device. Each device uses the same total order as the merge: the role, then `device_order`, then the slug. So 2 remote devices that are not in `device_order` agree on one resolver. It finds the author of each version from its sha256 journal of its own writes (`~/.aw/journal/<workspace id>.jsonl`: each write of the files layer, and each local change that the engine reports, so a human edit counts) and, for knowledge, from the change logs. With 2 devices, the copy is of the device that is not the winner in the copy name. It applies the priority rule, writes the winner, removes the copy and stores the other version in the history store (measured: 1.6–1.9 s). A version that the resolver writes for another device is not a write of this device, so it does not go to the journal. When no author is found, AW keeps the Syncthing winner. For a knowledge file, the knowledge store writes the winner and appends a `replaced` change by `aw@<device>` from the lost version (section 5). So each device explains the new version, and Undo gives the lost version back.
4. A file that fails its schema: the index keeps the last valid version. The merge keeps it through an index rebuild, and awd gives the documents of the index to the merge at start, so it also stays after a restart. A device that never read a valid version has none. The Inbox shows the error with "Open file" and "Restore last valid version". Each repair writes a line to device health; a repair of a device-owned file also creates "Sync problem".

### 6.7 Engine on Android
1. **Build**: `android/engine/scripts/build-libawsync.sh` (Gradle task `:engine:buildEngineLibs`, `task android:engine-libs`) builds `libawsync.so` (arm64-v8a, x86_64) from the pinned Syncthing source tarball with the recipe of `tech-stack.md` 1.2, about 35 MB extracted. `android/engine/engine-version.properties` pins the tag (the tag of the computers), the sha256 of the source tarball and of each Go archive, the Go and NDK versions, a fixed `SOURCE_DATE_EPOCH` and the sha256 of each built file. The app packs the files with `useLegacyPackaging = true`; they are never in git. A CI job that builds them comes with the release pipeline.
2. **No fork code**: AW writes its own Kotlin REST client. No MPL-2.0 file enters the AW app code. The app ships the Syncthing license and a link to the source tag.
3. **Start**: the app starts the binary as a child process with `STHOMEDIR` (`<files>/sync`) in app-private storage, `STNOUPGRADE=1`, `STMONITORED=1` (one process: the app is the monitor) and the random API key. The first start uses the steps of 6.1, with the phone values: the phone slug as the name, a reconnect interval of 20 s. The supervisor has the rules of 6.1 (ping every 10 s, restart with a backoff from 1 s to 60 s, a stale engine of an earlier app process is stopped only when its command line has `libawsync.so` and the home). REST listens on the Unix socket `<files>/run/sync.sock` (spike S3); the Kotlin client (Ktor, OkHttp engine) connects through `LocalSocket`. Fallback: when the engine runs but the socket gives no ping in 2 starts in a row, the app writes `127.0.0.1` on a random port with HTTPS, and the client trusts only the engine certificate `<files>/sync/https-cert.pem`.
4. **Storage**: the `tasks` and `knowledge` folders in app-private storage, `<files>/aw/<workspace id>/`. So the app needs no all-files access. The phone has no `secure` folder and no file versioning; the ignores are `*.aw-tmp` and, in `tasks`, `/*/artifacts`. The peers come from the signed device records: each record that is not revoked and is not this phone, from the kept records of the index of each workspace, or from the records of the pairing response (`<files>/records/<ws>.json`) until `tasks` syncs. A workspace with no record yet does not change the list. The app keeps the list in `<files>/sync-peers.json` (the format of awd). The engine also runs with no workspace while a pairing is open, and the config step keeps the device of an open pairing. After each engine start and each disk event of the engine (`RemoteChangeDetected`, `LocalChangeDetected`), the app waits 500 ms and then runs the merge and writes the Room index.
5. **Run pattern**: one foreground service with a permanent, low-priority notification ("AW · syncing with 2 devices") runs the engine while the phone has a paired workspace. Each time the app opens, the app restarts the engine and sets the reconnect interval to 5 s. In battery mode "Restricted", sync stopped in Doze and came back only after a force-stop and an app start. So the app shows a warning for this mode, with a link to the setting (`ActivityManager.isBackgroundRestricted()`; the notification shows the warning until the screens of android-ui do). "Sync now" on the phone has a timeout of 60 s and starts the engine when it does not run.
6. **Why not short `dataSync` bursts** (the earlier research, AN14–AN19): with the foreground service, a file arrived in 3.1 s in deep Doze, and the engine used about 50 MB RAM and 0.26 % CPU when idle. A burst needs a push to start, and push is not verified (S1). Only the phone dials, so a cold burst adds a connection wait to each answer. Android 15 limits `dataSync` to 6 h per 24 h, so the service type is `specialUse`. Risks: Play review (S4) and battery use (S10). Fallback: the burst pattern.
7. **Permissions**: the pairing screen explains `ACCESS_LOCAL_NETWORK` and asks for it on Android 17 (API 37) before the join. A refusal does not block the join; sync then uses Tailscale or the internet path. The QR scan uses the ML Kit code scanner of Play services, so the app needs no camera permission. **Settings text**: "Across networks, Syncthing uses community discovery and relay servers. They see your IP address, your device ID and the traffic volume, not your data. Turn them off to use LAN or Tailscale only."

### 6.8 Revoke a device
1. On the desktop app or the phone, the human selects "Revoke device". The confirmation names the sessions that stop and says that the revoked device keeps its copy of the files.
2. The device with the master key writes `revoked: true`, a new sequence number and `revoked_at` (its HLC) to `devices/<device>/device.yaml` (`aw device revoke <device>`). Each awd and the phone app read the record and call `DELETE /rest/config/devices/<sync id>`. Online devices disconnect within 10 s. Before its own drop, the revoking awd keeps the revoked device as a peer until its engine reports that the device has the new record (`availability` of `GET /rest/db/file`), the device is not connected, or 10 s pass. So an online revoked device reads its revoke and stops its sessions, in each of its workspaces: the revoking awd drops it as a peer of each folder. A device that is offline at the revoke never gets the record: it keeps its sessions and its copy, and gets no more changes. The reply says so (`delivered: false`), and the CLI and the desktop tell the person to stop its sessions on that device. The drop also runs when a later revoke step fails. The merge does not apply an event of the revoked device whose HLC sorts after `revoked_at` (reason `device_revoked`); its earlier events stay. Its tasks show "Paused: <device> was revoked" with "Change assignee": the presence lists each task that is not done or archived and whose assignee device (else claim device) is revoked, with `device_revoked` and the `revoked_at` time. On the desktop the task goes to "Needs you", and the app shows one notification; no device sends a push for it.
3. awd makes a new workspace credential key, seals it to each remaining computer and encrypts `secure/credentials/` again. The sealed file of the revoked device keeps the old key, which opens no new file. The Inbox lists the credentials that the revoked device had, with "Rotate".
4. Each awd uses only a device record with a valid master-key signature over the record as written, and the highest sequence number that it read. A record that fails keeps the last valid record and shows the issue `bad_signature` or `old_sequence`. Each workspace has its own sequence numbers, so awd compares them only inside one workspace, and a device that one workspace revokes is no peer of any folder.
5. A revoke is final. The merge keeps a revoke when its file is removed (issue `revoke_removed`) or when a valid record without the revoke replaces it (`old_sequence`). The device with the master key writes the newest record again when the file on disk is missing, refused or older, so a device that was offline during the revoke gets it through sync. A revoked slug, device key or sync device id never pairs again. Each computer opens its credential key again when `secure/keys/<device>.age` changes, so the rotation needs no restart.

### 6.9 Remove a project
A person removes a project in Project settings ("Remove the project…") or with `aw project remove <slug> --yes` (openspec project-remove). The remove frees the slug, so a project that points to a wrong folder can be added again.
1. **Preview.** `GET /v1/workspaces/{ws}/projects/{project}/removal` and `aw project remove <slug>` (no `--yes`, exit code 1) name the open tasks and the running sessions with their device. The desktop dialog asks the person to type the slug.
2. **Event.** `POST /v1/workspaces/{ws}/projects/{project}/remove` writes one workspace event `project.removed {project, name, document}` by `human@<device>` to `tasks/log/<device>.jsonl`. `document` is a copy of `project.yaml`. It is a person route; the merge applies the event only from a person (`not_human`). A log line is never lost in the conflict resolver, so a concurrent edit of `project.yaml` cannot undo the remove.
3. **Merge rule** (awd and the phone, case `contracts/fixtures/merge/project-removed`). With R the newest removal of a slug: the project is live when no R exists or its `added_at` (HLC) sorts after R. A task is removed when R exists and its `task.created` sorts before R, or its project is not live. So a task that another device creates at the same time (offline) goes with the project. The view lists only the live projects and tasks; `removed_projects` and `removed_tasks` hold the rest. A removed task is not an open dependency of another task (`open_dependencies`), so a task of another project does not wait for it. The next free key also counts the removed tasks, so no new task gets the key and the branch `aw/<key>` of a removed task.
4. **Each computer** acts on the merged view, as for a revoke (6.8): it stops its running sessions of the removed tasks (`session.ended` reason `stopped`, no wake branch, no `task.released`); it removes its own checkout of the slug from `bindings.yaml` when the checkout `bound_at` (HLC, set by each checkout change) is missing or sorts before R; it removes each AW worktree of a removed task that is clean and whose branch has no unpushed commit (`git worktree remove`, or the session host for Orca), then deletes the branch. An unpushed commit is a commit that no remote branch and no other local branch has. A dirty worktree, a worktree whose HEAD has a commit that no branch has (a detached HEAD), or an unpushed branch stays: the reply of the removing device lists it, and another device writes a system comment on the task and a log line. AW removes no folder of a checkout session or a folder session. `~/.aw/removed/<workspace id>.json` keeps the done removals.
5. **Add again.** `addProject` refuses only a live slug. It writes a new `project.yaml` with `added_at` after each removal of the slug; the old tasks stay removed.
6. **Recovery (principle 8).** AW deletes no task folder, task log or `project.yaml`. The task folders stay in `tasks/<task-id>/`, the event keeps the old `project.yaml`, and the knowledge files of the project stay. `aw task show <key>` and `aw thread <key>` (`GET /v1/workspaces/{ws}/tasks/{task}` and its thread) still read a removed task; a write to it gives 404. To get a removed project back, add the slug again and create its tasks again from the files; a later phase can add "Undo remove".

## 7. Pairing
One code carries the AW identity and the sync device id. A device with the master key (the desktop app on the main device, or the phone) shows it.
1. The human selects "Add device" or "Pair phone". The app shows a QR code and the same data as text (`aw1:…`), valid for 10 minutes. The code holds the user id, the master public key, the device key and sync device id of the showing device, its LAN and Tailscale addresses, a one-time secret and the expiry.
2. On the new device, the human scans the QR code (phone) or runs `aw pair -` over SSH and pastes the code (remote device; the code holds the one-time secret, so it stays out of the shell history). Both engines use a reconnect interval of 5 s until the pairing ends. On a computer, `aw device add` shows the code (`--qr` also prints the QR code), and the apps use `POST /v1/workspaces/{ws}/pairing`. The code is used once: the first valid request uses it. A workspace has one open pairing at a time.
3. The new device creates its device key and its engine identity. It adds the showing device to its engine and offers a pairing folder `aw-pair-<nonce>`. The folder holds a request with its keys, its sync device id, its proposed slug, a signature with its device key and an HMAC with the one-time secret. `aw pair --path <folder>` names the workspace folder itself, which must be missing, empty or the folder of the same workspace. `aw pair --in <folder>` (and the default `~/AW`) names a location: AW uses `<location>/<name>`, or `<name>-aw1` when that name is in use (section 3).
4. The showing awd reads the pending devices and the pending folders every 1 s while a pairing is open (`GET /rest/cluster/pending/devices`, `/folders`). It adds a pending device with no workspace folder, accepts only the folder of the nonce, and checks the HMAC and the signature (the public keys of the devices are not secret). Both screens show the same 6-digit check code from the keys of the showing device and each field of the request (both keys, the sync device id, the slug, the role, the nonce). The human selects "Approve device", or runs `aw device approve <pairing> <check code>` with the code from the new device. While the approval runs, the code does not expire and the pairing cannot be cancelled. Accepted risk: the requester chooses the fields of the check code, so an attacker with a leaked code who also sees the real check code can try about 1,000,000 requests for the same code, and must then send the first request.
5. The showing device signs the device record. It adds the new device to the engine and shares `tasks` and `knowledge`, and `secure` for a computer. Each other device adds it when it reads the record (full mesh). For a phone, the showing device seals nothing yet: the master key on the phone (sealed to the phone's device key in the pairing folder) is a later task. For a computer, it seals the workspace credential key to the new device key (`secure/keys/<device>.age`) and copies the knowledge history store (each version, not `seen.json`) into the pairing folder. `response.json` has the newest signed record of each device of the workspace, revoked ones too. Approve refuses a slug, device key or sync device id of a revoked record or of the showing device.
6. The new device checks each record with the master public key of the code, saves the identity, sets its slug and role, adds the workspace folders (the folder that `join` chose: `--path`, or `<--in location>/<workspace name>` with the `-aw1` suffix rule, default location `~/AW`; the name has no path separator and no leading dot), waits for `tasks/workspace.yaml`, checks that its id is the workspace id of the code, and registers the workspace. AW removes the pairing folder. An awd restart ends an open pairing. The new device shows "Synced with MacBook Pro · 2 s ago". Measured on a LAN: connected in 0.3 s, folder shared in 2.6 s. With "LAN and Tailscale only", the 2 devices need the same LAN or Tailscale once.
7. **The phone** (`android/control` `PhonePairing`, the same formats as `shared/identity` in `android/identity`): the screen "Pair with a computer" (the first screen when the phone has no workspace, and "Join another workspace" on Devices) scans the QR code with the ML Kit code scanner, or takes a pasted code, and asks for the name of the phone (prefilled with the phone model; the slug comes from it, for example `pixel-9`). A phone that paired before asks for no name: it joins each next workspace with its stored slug and name, so it has one slug in each workspace. After the join the app shows the new workspace. The engine starts for the pairing also with no workspace. The phone sends the request with `role: "mobile"`, shows the check code at once, and the human approves on the computer. The phone checks the records as in step 6 (its own record must have the role `mobile`), saves `<files>/identity.json`, `<files>/device-slug` and `<files>/records/<ws>.json`, sets its peers from the records, adds the 2 folders, waits for `tasks/workspace.yaml` and writes `done.json`. Its device key (Ed25519 and age X25519) is made in software with Tink and kept in `<files>/device-key.bin`, encrypted with a non-exportable AES-256-GCM key of the Android Keystore: the platform keystore has no Ed25519 before API 33. A Keystore key that a restore lost gives a new device key, and the phone pairs again as a new device. After the pairing the phone merge checks the record signatures with the rules of 6.8 (`bad_signature`, `old_sequence`, `revoke_removed`).

## 8. Push without a relay
Push is required in phase 1 (task-model decision §5.4). Spike S1 must pass before the phone release.
1. Each computer creates a VAPID key pair (P-256). The private key stays on that computer, in `~/.aw/keys/vapid.json` (0600), not in the OS keystore. The computer writes the public key (uncompressed point, base64url with no padding) as `vapid_public_key` to its own `devices/<device>/bindings.yaml` (field of `bindings.v1`). The key pair is in `~/.aw/keys/vapid.json` (0600); awd makes it at its first start and writes the public key again when the bindings lose it.
2. After pairing, the phone registers one UnifiedPush instance per computer and workspace (instance name `<workspace id>/<computer>`), with the VAPID public key of that computer, for every joined workspace and not only the shown one. The registration runs in the app process, also with no screen open. A new endpoint in a new app process keeps the VAPID key of its `push.yaml` entry. A failed registration shows "Push is off: the registration failed" and is not sent again with the same key until the app restarts. The Play build uses `embedded-fcm-distributor` 3.x: it registers with FCM through Play services with the VAPID key as the sender, so the app has no Firebase config file. The fallback is any UnifiedPush distributor, for example the person's own ntfy server. The app keeps the distributor that answered before; else it takes its own embedded distributor, else the first UnifiedPush app, with no picker. No AW server is in the path. The phone writes the endpoints and its encryption keys to `devices/pixel-9/push.yaml` (only the phone writes it):
   ```yaml
   kind: push
   schema: 1
   device: "pixel-9"
   subscriptions:
     - computer: "ubuntu-01"
       endpoint: "https://…"          # the UnifiedPush endpoint
       p256dh: "<base64url>"           # RFC 8291 public key of the phone
       auth: "<base64url>"             # RFC 8291 auth secret
       vapid_public_key: "<base64url>" # the key that the instance was registered with
       distributor: "<package>"        # or null
       updated: "2026-11-23T10:00:00.000Z"
   ```
   The owner device of a gate sends to the subscription with its own `computer` slug, and only when `vapid_public_key` is its current key. The schema of the file is `push.v1`; awd skips a file that does not pass it.
3. At a gate, the owner device encrypts the preview with RFC 8291 (`aes128gcm`): the JSON `{"event", "task", "key", "kind", "gate_kind", "text"}` (event id, task id, task key, kind, gate kind, one line), at most 3 KB. `kind` is `gate` (a gate or "Assign task"), `done`, `login_expired` or `login_ends`; `gate_kind` is null when `kind` is not `gate`. It sends it with a VAPID header (RFC 8292, an ES256 JWT for the origin of the endpoint, valid 12 h; the contact is always `mailto:noreply@example.com`, so no personal address leaves the computer), `Urgency: high` and a TTL of 24 h. The sender is `plugins/push-webpush` (`@noble`, tested with the vectors of RFC 8291 appendix A). The owner sends the pushes and reminders of the gate table (`workflow.md` 3) and one push "Done" per task; `~/.aw/push/<workspace id>.json` (mode 0600) records each sent push, so a restart sends none twice, and a gate that opened more than 10 min before the check gets only its reminders. A 404 or 410 reply means that the phone registers again; AW does not retry a push (the reminder is the retry).
4. The phone decrypts the push (the UnifiedPush connector does it) and shows the notification at once: the title `AW-7 · Answer question` (from `kind`: `AW-12 · Done`, `AW-12 · Login expired`, `AW-12 · Login ends soon`), the text the line, the tag the event id; a tap shows the workspace of the instance and opens `[Inbox, Task(id)]`. The app reads the task of a tap only from its own notifications (a component that the manifest does not export); another app cannot open a task. A push of another form shows "AW · A gate needs you". It starts the foreground service when it does not run and syncs for at most 15 s. When the gate arrives, the card shows the full plan and the effect of each answer.
5. The answer goes to the phone's own log and a targeted scan. The card shows "Answer sent, waiting for ubuntu-01" until `gate.resolved` arrives. When the owner device is offline, the card says so. R2 removes this wait in phase 2.

## 9. Sessions and continuity
Phase 1 builds all of `architecture.md` 4.5 and 4.6. This section gives the exact rules.

### 9.1 Launcher
1. awd writes the first input to `~/.aw/sessions/<session>/first-input.md`. User text never goes into a shell command line. The folder (0700) also has `session.json` (the record: claim epoch, pids, launch flags), `launch.json` (the arguments of `aw-launch`), `context.md` (SessionStart), `settings.json` (the session settings) and `spool/` (hook events). Each file has mode 0600.
2. awd opens the window with exec-form arguments through `execa` and no shell: `tmux -L aw new-window -n aw-<task-id> -- <daemon>/bin/aw-launch <session>`. The tmux config of the server has `remain-on-exit on` and `exit-empty off`, so AW can read the exit status of a dead session. The working folder is the git worktree `~/.aw/worktrees/aw-<key>` on `aw/<key>` (a folder of an older AW keeps its name `<task-id>`), made from the project checkout in `bindings.yaml` of the device, or the folder of the session options (9.1.7).
3. `aw-launch` is a fixed Node script (`daemon/src/bin/aw-launch.ts`). It reads `launch.json`, checks `/readyz` on the awd socket (waits up to 10 s, else exits with code 3), writes the trust entry (item 5), exports `AW_SESSION`, `AW_TASK`, `AW_WORKSPACE`, `AW_HOME`, `PATH` with the plugin `bin/` first and `CLAUDE_CODE_NONBLOCKING_STDOUT=1`, and replaces itself with `claude` (`process.execve`, no shell): `claude --session-id <uuid> -n <key> --plugin-dir <aw-plugin> --settings <session-settings> --permission-mode <default|acceptEdits|bypassPermissions> --allowedTools <the agent command rules> "mcp__plugin_aw_aw__*" -- <the text of first-input.md>`. So the pane pid is the claude pid. It also exports `AW_MCP_URL` (from `~/.aw/run/mcp.port`) and `AW_MCP_TOKEN` (from `mcp-token` of the session); the token is in no command line and not in `launch.json`. When awd has `CLAUDE_CONFIG_DIR`, the session gets the same value, so awd and the agent use one transcript folder; with no value awd sets none, because the variable also moves the state file of Claude Code (`~/.claude.json`). The session settings file names `bin/aw-statusline` of the plugin as the `statusLine` command (9.6.9).
4. Resume: `exec claude --resume <uuid> <the same flags> -- "<continue message>"`. The message is the last argument, after `--`. With another order, the continue message was lost once.
5. AW pre-trusts each worktree that it creates (`architecture.md` 4.6.2), because no hook reports the "trust this folder" screen. On a Claude Code version that the contract tests do not cover, aw-launch writes no trust entry: awd answers the trust screen ("Yes, I trust this folder") once per window, before the first SessionStart. It presses Enter only when the cursor is on "Yes, I trust this folder" (it moves the cursor down once at most), because the option order of that version is not known; else a comment asks the human to answer in the terminal. The trust entry re-reads `~/.claude.json` just before its rename (a running Claude Code can write it at the same time), writes the target of a symlink, and keeps the last 5 backups.
6. The allow rules are necessary: without them, each `aw ask` waited for a permission click. They cover only the agent commands: `Bash(aw ask *)`, `Bash(aw message *)`, `Bash(aw stage *)`, `Bash(aw artifact add *)`, `Bash(aw handoff *)`, `Bash(aw thread *)`, and the work loop `Bash(aw approach *)`, `Bash(aw ready *)`, `Bash(aw result *)`, `Bash(aw done *)`, `Bash(aw gate open *)` and `Bash(aw task create *)`, the test slots `Bash(aw slot acquire *)` and `Bash(aw slot release *)`, and the knowledge commands `Bash(aw learn *)`, `Bash(aw kb write *)`, `Bash(aw kb search *)`, `Bash(aw kb show *)`, `Bash(aw kb list *)` and `Bash(aw kb context *)` (awd refuses an agent write to `shared/` or to a rule). A rule for the whole CLI (`Bash(aw *)`) let the agent run `aw gate answer` with no prompt, so it could answer its own gates as the human (principle 4). The CLI also refuses each command of a person (`aw gate answer`, `aw task assign|edit|archive`, `aw kb accept|reject`, `aw session stop`, `aw queue`, `aw service install|uninstall|move-keys`, `aw engine install`, `aw doctor`, `aw workspace init|rename|edit|remove`, `aw project add|edit|archive|unarchive|remove`, `aw binding set|remove|slot|orca`, `aw sync community on|off` (the read is allowed), `aw identity`, `aw device`, `aw pair`, `aw credential`) when `AW_SESSION` is set (exit code 1). awd also refuses each person route to a session caller (5.10): the session token, or a process of the session tree with no token.
7. **Session options** (openspec session-options, `workflow.md` 4.2.1). `task.created` and `task.assigned` carry `session_options {permission_mode: default|accept_edits|skip|null, agent_teams, work_in: worktree|checkout|folder, folder}`; the merge keeps them only from a person, and the newest one replaces the object. `project.yaml` has `permission_mode` (default `skip`: a missing value counts as `skip`, owner decision 38, openspec polish-skip-default); a project `skip` counts only for a task whose `task.created` is from a person. `tasks/workspace.yaml` has `new_project_permission_mode` (default `skip`, synced; a missing value counts as `skip`): a new project gets the mode of the add request (`aw project add --permission-mode`), else this value (openspec permissions-default). Only a person sets it: desktop Settings → New projects, or `aw workspace edit --new-project-permission-mode`. A change does not change existing projects. The session record and `launch.json` keep the mode and the teams value; `session.started` writes `permission_mode`, `agent_teams` and `work_in`, and the task view shows them with `cwd` and `branch`. The session settings file has the deny rules `Bash(aw <c>)` and `Bash(aw <c> *)` of each person command, and for `skip` `"skipDangerousModePermissionPrompt": true` (without it the warning dialog of bypass mode blocks the start; spike of 2026-11-24 on 2.1.330 and 2.1.331); for agent teams `env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"` and `teammateMode: "in-process"`. The spike showed that a deny rule and a PreToolUse deny hold in `bypassPermissions`, that the PermissionRequest hook does not fire there, and that `sh -c "aw gate answer …"` passes a deny rule. So `aw-hook` runs the AW guard (`daemon/src/sessions/guard.ts`) before each tool call, in each mode and with no awd call: it denies a Bash command whose text names a person `aw` command at a word start (also inside quotes), the text `awd.sock`, a workspace folder, or a path in AW_HOME outside `worktrees/` and the credentials folder of the session (also as `~/…` or `$HOME/…`, with `..` out of these folders, or as a relative path with `..` from the working folder); Edit, Write, MultiEdit and NotebookEdit on a path in AW_HOME outside `worktrees/` or in a workspace folder; Read, Grep, Glob (also the folder of its pattern) and LS in AW_HOME outside `worktrees/` and the credentials folder of the session. File tool paths count with their symbolic links resolved, and the hook prints its deny also when it cannot write its spool file. awd writes one comment "AW denied <tool>: <command>. Reason: <reason>." Work in: `checkout` runs `git switch aw/<key>` in the project checkout after the prepare of 9.6, and refuses a second running session in the same checkout, a branch that another folder has, and local changes that git refuses; a clean tmux worktree that AW made for an earlier session of the task gives the branch free (`git worktree remove`, no force; one comment "AW removed the worktree …"); a later "Separate worktree" session refuses a branch that the project checkout has; `folder` runs the session in the absolute folder as it is (no branch, no checkpoint push, no commit of unpushed work on a move) and refuses a missing folder, a folder in AW_HOME or a workspace folder, a folder that holds one of them (the user home, for example), and a folder that is in, or holds, the folder of a running session of another task. A session in the checkout or another folder runs in tmux (Orca opens a terminal only in an Orca worktree). The phone "Stop session" writes `session.stop_requested {session}` (a person event; the merge rejects it from another actor with `not_human`); the session device stops that session with the reason `stopped`.
8. **Task actions** (openspec task-actions, `workflow.md` 6.1). The awd service has one method for each action: `stopTaskSession` writes `session.stop_requested` for the running session on any device; `archiveTask(ref, {stop})` refuses a running session without `stop` (`conflict`, with the device and `aw task archive <key> --stop`), and with `stop` writes `session.stop_requested` before `task.archived`; `unarchiveTask` writes the new event `task.unarchived {}`. The person routes are `POST /v1/workspaces/{ws}/tasks/{task}/stop`, `.../archive` (body `{stop?}`) and `.../unarchive`; the commands are `aw task stop`, `aw task archive [--stop]` and `aw task unarchive`. The merge folds `task.archived` and `task.unarchived` in merge order (the newest wins). The session device stops the session of an archived task with the reason `stopped` (before: `moved`), so the claim stays and an unarchive starts no session.

### 9.2 First input and context
1. A Discuss session gets the first message as is. A later session (a subtask, or a task that moved) gets: the first message, the confirmed approach word for word, and "Read `aw thread <key> --ancestors` before you act." The first message is first, so a command such as `/opsx:apply` stays at the start.
2. The SessionStart hook gives the task fields, the gate state and the knowledge context of `aw kb context <task>` (5.9), at most 10,000 characters. A knowledge list that does not fit is cut at a line end, and its last line names `aw kb context <key>`. Claude Code cuts longer context to a file path and a preview. `aw thread` prints long threads in pages (`--from <n>`).
3. A subtask starts at Ready with the confirmed approach of its parent. Its workflow can still open "Confirm approach" for its own approach (task-model decision §5.2).

### 9.3 Hooks
| Hook | AW writes |
|---|---|
| SessionStart | `session.started`: cwd, plugin dir, credential names, branch, pids |
| UserPromptSubmit | `message.human` with the raw text and the delivery id |
| Stop | `message.agent` from `last_assistant_message`. A reply that ends with a question opens the gate "Reply", unless a gate "Answer question", "Confirm approach" or "Reply" of this session opened in the same turn (after its last `message.human`) is still open. An old gate (an "Approve command" after its timeout, a gate that the human answered in the terminal) does not stop it. |
| PreToolUse `AskUserQuestion`, `ExitPlanMode` | Gate "Answer question" with the options and `questions` (each question with its header, multiSelect and option descriptions), or "Confirm approach" with the plan (`approach/v<n>.md`). The hook makes the gate id, so the deny works while awd is down: "AW sent this to the human as gate <id>. End your turn now." |
| PreToolUse (other tools), PostToolUse | The interrupted step of a resume: the last PreToolUse with no PostToolUse |
| PermissionRequest | A rule, or the gate "Approve command" (9.5) |
| Notification | `permission_prompt`, `idle_prompt`: a dialog is open (9.4) |
| StopFailure, SessionEnd | Pause cause; transcript copy |

AW reads agent output only from hooks and the transcript, never from a terminal screen. The Orca terminal was 2 columns wide (9.9). The hook command `aw-hook <Event>` writes one JSON file per event to `~/.aw/sessions/<session>/spool/` and exits; awd reads the spool in name order at start and twice per second, so no event is lost while awd is down. awd writes the events of a hook at once (not in the 1-second buffer) and moves the spool file to `spool/done/` only after them, so a kill of awd loses no event; a retry of a file does not write its events again. The UserPromptSubmit source is `first` (the first input), `answer` (`[AW answer <gate>]`), `phone` or `typed` (`[AW message <id> from <device>]`, by the role of the device) or `typed`. A prompt that starts with `[AW resume]` is written as `session.resumed`.

### 9.4 Safe delivery
1. One function delivers each answer, message and notice into a session. It sends only when no dialog is open: no waiting PermissionRequest hook, no `permission_prompt` Notification with no later hook event, and no dialog at the bottom of the visible screen (the scrollback keeps old dialogs). A dialog is found by its layout, never by free text: a footer ("Esc to cancel") in the last lines, a selection cursor on an option (`❯ 1. Yes`) above it, and no prompt line below it. The agent text of the last turn can hold the same words ("Do you want to ...?"). A dialog on the screen that blocks a text for 90 s gets one comment "Answer waits". Typed keys go to an open dialog. A busy turn is safe: Claude Code queues the text, and submits it when the turn ends. So AW counts no retry from a UserPromptSubmit to the next Stop (or `idle_prompt`).
2. A text counts as delivered when the log has a `message.human` with its delivery id. So after an awd restart, awd finds each resolved gate and each `message.sent` with no confirmation and delivers it once more.
3. It pastes the text with `tmux load-buffer` and `paste-buffer -p`, then presses Enter once. A multi-line text stays one input.
4. Each text starts with a delivery id, for example `[AW answer <gate-id>]`. The UserPromptSubmit hook confirms the id. AW makes at most 3 attempts, 30 s apart, then writes the comment "Answer not delivered" with the pane snapshot. The session record keeps the ids that failed, so the next texts go on and a restart does not paste a failed text again.
5. The phone can send free text to a running session through the same function (task-model decision §5.3).

### 9.5 Permissions, gates and ready
1. Each permission request gets a unique request id (`p-<uuidv7>`). Each answer names that id. A counter id approved the wrong command in the verification.
2. "Approve command" (options "Allow once", "Allow for this task", "Deny") waits 120 s in the hook, then denies with `interrupt: true`. The gate stays open while the agent waits on it. A later "Allow" becomes a one-time approval of the same tool and input. AW delivers "Approved: run it again", and the hook allows the matching retry once. The owner device closes the gate with "Denied after 120 s" when the session starts a new turn (a `message.human` of the session that is not the delivery of a permission gate, timed by its hook) or opens another permission request more than 120 s later, and with "Session ended" when the session ends (`workflow.md` 3, rule 4; `daemon/src/loop/stale-gates.ts`). "Allow for this task" adds a rule: the same tool, and the same command for `Bash`, the same file for a file tool (`file_path`, `notebook_path` or `path`), or the same whole input for another tool. The wait counts from the gate open: a retry of the hook after an awd restart waits only the rest of the 120 s, and awd ends a waiting request with 503 when it stops. While awd starts, a running session gets 503 (the hook tries again), not 403. The gate event keeps the tool, a summary and the sha256 of the input, never the input (a Write of a large file does not fit in a log line); the full input stays in `~/.aw/sessions/<session>/requests/<gate>.json` (0600) for the rule of "Allow for this task".
3. A deny also goes to the agent as the next input of the human: "Denied by human@pixel-9: <reason>". The model reads a hook deny only as a tool error.
4. AW sends "Start implementing" only after `aw ready` passed on the implementing device: a `task.ready` of this device after the claim of the session, no open missing item (each `--missing` item is a question gate, listed in `task.ready.gates`), approach confirmed (for a subtask with no own approach: the parent approach), assignee set, no open dependency, `knowledge` and `secure` complete with each connected computer (the engine `completion` only for the text). A new session on another device runs `aw ready` again (`workflow.md` 4.7). "Start implementing" is a notice (`message.sent` by `aw@<device>`, delivered as `[AW notice <id>]`), once per session.
6. Stage changes (`task.stage_changed` by `aw@<device>`, the owner device): the first claim (Discuss, or Ready for a subtask that starts with the parent approach), "Confirm" of "Confirm approach" (Ready), the ready checks (Implement), `aw result` (Review), "Request changes" of "Approve result" (Implement). The task is Done at the first Stop after "Result approved" was delivered, or after `aw done`. When the approval reached the agent while its result turn still ran, AW sends one notice "Result of <key> approved …" as a new turn, and the task is Done at the Stop of that turn.
7. Credentials at the session start: the session device writes the value of each credential name of the task to `~/.aw/sessions/<session>/credentials/<name>` (0600) at each window open and sets `AW_CREDENTIALS_DIR`. A name with no value gets one comment. The values come from the credential service (10.2): each file `secure/credentials/<name>.age`, opened with the credential key of this device. Each value and each session token is in the redaction of the events before the session starts (`[redacted:<name>]`, `[redacted:mcp-token]`); a value that a session got stays in it while awd runs. No log line has a value.
5. The push, timeout and reminder rule of each gate is in the gate table of `workflow.md` section 3.

### 9.6 Claims, presence and moves
1. **One session per task.** A device starts or resumes a session only after it writes `task.claimed {epoch, device, session, based_on}` with an epoch above each epoch that it knows. The merge order picks the same winner on each device. A claim counts only from the device of the current assignee; the merge ignores a claim from another device with the reason `not_assignee_device` (`decisions/2026-11-23-manual-move.md`).
2. On each wake and reconnect, awd first reads the merged logs, then checks its sessions. A session with a lower epoch stops and shows "Moved to ubuntu-01".
3. **Presence.** Each awd appends a heartbeat to `devices/<device>/heartbeat/<date>.jsonl` every 30 s. Another device marks it offline when no new heartbeat arrived for 90 s, by its own receive time. After an awd start or an index rebuild, the first receive time of a device is the earlier of the local time and the HLC time of its last heartbeat. Then its running tasks show `device_offline`. The tasks wait, also after a long time: AW opens no gate and moves no queued task.
4. "Move to" (and "Assign to another device…" on a paused task) is a human `task.assigned` and follows `architecture.md` 4.3.4. The new session starts from the checkpoint branch in `task.yaml`. Only the session with the highest epoch pushes it, with `--force-with-lease`.
5. **A laptop that wakes after the human moved its task** pushes its unpushed work as the branch `aw/<key>-<device>-<time>` and writes a thread comment (`comment.added`) with the branch name. It is no longer the owner, so a `message.*` event would not count. AW never drops this work (task-model decision §5.5).
6. Before an agent implements on a device, `knowledge` and `secure` must be complete there. Else the task shows `waiting_for_sync`. An AW update stops the engine for a few seconds, and sessions continue in tmux.
7. "No recent update" shows when a session runs in a turn (not at a gate, not paused, not idle after a Stop) with no hook event and no pane change for 2 min (the spinner line of Claude Code and each number on the screen do not count as a change): every 30 s awd compares the time of the last hook event and a hash of the visible screen, and writes `task.progress` "No recent update for 2 min. Last terminal line: <line>" once per quiet period. After 15 min of quiet it writes "Busy for 15 min: <step>" for a tool that runs, or opens "Take over terminal" for a dialog on the screen that no hook reported. AW does not read the screen of an Orca session (9.9.4): its quiet time counts from the hook events only, there is no last terminal line, and after 15 min of quiet in a turn (no Stop) with no tool that runs, AW opens "Take over terminal" that names the Orca worktree. AW never kills a live process; a dead process is the pane check (9.7.3). Other devices add 8 s for sync (6.3).
8. **Pauses** (`architecture.md` 4.6.5). The session device writes `task.paused {cause, resumes_at, next_step, needs_human}` only when the cause or the text changes, and `task.resumed` when the cause ends: `usage_limit`, `usage_limit_weekly`, `continue_cap` (9.6.9); `agent_error` (a StopFailure that is not a usage limit: a notice to continue after 1, 2 and 4 min; the 3rd failure in a row opens "Take over terminal" and needs the human; a Stop ends it); `device_restart` (a window that opened before the boot of the computer: the pause before the resume, then `task.resumed` and the comment "<device> restarted at 03:12. AW resumed the session at 03:13." at the SessionStart); `login_expired` (9.6.10). `device_offline` is a view of the presence, with no event: the offline device cannot write. A revoked device stops its sessions and claims nothing; its later events do not count (`revoked_at`). A session record that leaves `running` loses its `credentials/` folder.
9. **Usage limits.** `aw-statusline` writes `rate_limits.five_hour` and `rate_limits.seven_day` (`used_percentage`, `resets_at` in Unix seconds) to `usage.json` of the session when they change, then runs the `statusLine.command` of the user settings of Claude Code (`AW_USER_STATUSLINE`) and prints its output. A StopFailure `rate_limit` gives `usage_limit_weekly` when the 7-day window is at 100 % or the reset is more than 24 h away (AW continues at `resets_at` + 2 min with a notice), else `usage_limit` (Claude Code continues by itself; AW continues itself only after `quota_auto_resume_disabled`). `quota_auto_resume_fired` and the next prompt or tool event write `task.resumed`; `quota_auto_resume_stale` gets an Enter in tmux; Orca sends no keys, so for an Orca session AW continues at `resets_at` + 2 min, as after `quota_auto_resume_disabled`. A dead window waits for the reset before AW resumes it. The 4th AW continue in one session opens "Continue after usage limit" (Continue · Wait) and the pause `continue_cap`. AW pastes no text of the answer. "Continue" resets the count and continues at `resets_at` + 2 min (at once after the reset); "Wait" keeps the pause until the next message of the person.
10. **Sign-in.** awd runs `claude auth status --json` at the start and once per hour and keeps only `loggedIn`, `authMethod` and `loginExpiresAt`; a command with no JSON is "not known", not "logged out". An ended login pauses each running task `login_expired` (one push per task) and starts no new session. Less than 3 days before the end, each running task gets one comment and the device sends one push per end date.
11. **Agent queue** (`architecture.md` 4.6.8). `AW_MAX_WORKING` (default 2) working sessions per agent on a device, counted in all workspaces; a session at a gate or paused does not count. A new session (not a resume) waits while the count is at the maximum, the login ended, the 5-hour window is above 90 %, or the disk of `AW_HOME` is at `AW_DISK_FULL_PERCENT` (default 95). The order: the newest `queue.reordered` of the agent, then the creation order. A task that waits has no event (assignee and no claim). Each screen shows its position and one cause from the merged files, with the same rule on awd and on the phone (`daemon/src/continuity/queue-view.ts`, `android/control` `Queues.kt`, cases in `contracts/fixtures/queue/cases.json`): "Queued · 2nd for claude@ubuntu-01" and, in this order, "ubuntu-01 was revoked", "ubuntu-01 offline", "2 sessions working" (the real count), "login of claude ended", "5-hour usage at 93 %", "disk 96 % full", "2 sessions working" (the count with the tasks before it), else "starts soon". A task with open dependencies has no position and the cause "waits for AW-3". The person route `GET /v1/workspaces/{ws}/queues` and `aw queue` give the queues and the tasks with no assignee with their creator.
12. **Test slots** (`architecture.md` 4.7). `aw slot acquire <resource>` and `slot_acquire` give a lease from the device that has the resource in its bindings: `slot.acquired {resource, slot, fencing_token, ttl_ms: 1800000, task, session}`, a fencing token above each earlier token of the slot, or the queue position (first come, first served; an entry ends when its session does not ask again for 2 min; exit code 1). awd renews the lease of a running session at ttl/3 (the session heartbeat); a second acquire also renews it. `aw slot release` writes `slot.released`. A lease past its expiry is revoked (`expired`), the lease of a session that stopped is released, and after a reboot each lease from before the boot is revoked (`reboot`). Phase 1 gives a lease only to a session on the resource device: another device gets `not_available` with the device name, because the merge accepts slot events only from that device and no request event exists.
13. **Wake branch** (item 5): at a stop with the reason `moved`, AW commits the uncommitted changes of the worktree, and when HEAD has commits that no remote and no other local branch has, it creates `aw/<key>-<device>-<HHMM>` (the local time of the device) and pushes it to `origin`. The comment says "Moved to ubuntu-01. Unpushed work of macbook-pro is on aw/AW-12-macbook-pro-0315.", or that the push failed and the branch is local.
14. **Device health** (`architecture.md` 4.6.12): each session manager writes `tasks/devices/<device>/health.yaml` at most once per 60 s, and again only after a change or 10 min: boot time, versions, sessions (`running`, `gate`, `paused`, `ended`), the usage windows and the login end, the disk use, the queue limits `queue: {max_working, disk_full_percent, login_valid}` (other devices read them for the cause of a queued task), `sync: []` and `last_backup: null` (placeholders).

### 9.7 Process control
1. AW stores the exact pids of each session: the pane pid, the claude pid and the process group id. It never finds a process with `pgrep -f`.
2. A forced stop sends SIGTERM to the process group of the pane, and SIGKILL after 5 s. Then it kills each remaining descendant from the process table (read before the first signal). In the verification, background commands kept running after `kill -9` of claude. A resume first stops the process group of the dead agent. The stored pids are true only while tmux lists the pane with the same pid: with no such pane (a reboot, a `tmux kill-server`) AW signals nothing, because the pids can belong to other programs now. In a dead pane, AW signals only the members of the process group that started after the pane opened, one by one.
3. awd checks the panes every 5 s. A session that holds the accepted claim and has no live pane resumes. The resume count resets only after progress: a Stop or a PostToolUse hook, or 10 min alive (a SessionStart alone is no progress: an agent that dies after it would resume forever). After 2 resumes with no progress, or 5 resumes in one hour, the session is `failed` with `session.ended {reason: crashed}` (no person stopped it), the comment "Resume failed" and the gate "Take over terminal" (Resume again · Leave it stopped); "Resume again" sets it running and writes `session.resumed`, and the next check resumes it. The owner device writes the end only when the task shows this session. A dead pane with the exit status 3 (aw-launch: awd not ready in 10 s, for example after a reboot with many sessions) opens again after 30 s with no count, at most 20 times in a row. A session whose agent has no conversation yet (no prompt reached it and its transcript does not exist) cannot resume: it starts again with `--session-id` and the first input, at most 3 times, and this is not a resume. A resume of a session whose first input never reached the agent sends the first input as the message. When the resumes fail and the transcript of a session with a prompt is gone (30-day clean-up), AW starts it again with `--session-id`, the first input and the note "the earlier conversation of this session was lost; read `aw thread <key>`". Before a resume opens a tmux window, AW lists the tmux windows `aw-<task>`: it adopts a live one whose process (`ps -o pgid=,args=` of the pane pid) has the session id, and stops any other. A `tmux kill-server` alone does not stop claude: stop the sessions by process group first.
4. A task whose session cannot start (for example `git worktree add` fails, the checkout is not a git repository, or the window does not open) gets one comment with the cause, and AW tries again after 60 s with a new claim. With no tmux or no agent binary, AW looks again every 60 s, and each task of the agent on the device gets one comment with the cause. The other sessions of the workspace go on. A hook event that fails 5 times moves to `spool/failed/` with a comment, so the later events of the session go on. A text over the line limit (3.3.3) goes to `artifacts/<device>/text-<id>.md`, and the event keeps its first 2,000 characters and the file name.
5. A session stops when a person assigns its task again: `moved` when the task goes to another device, `replaced` when it stays on this device (another agent, or the same agent again: then one new session claims it). Both write `task.released`.

### 9.8 MCP server
1. SDK: `@modelcontextprotocol/server` 2.x, `@modelcontextprotocol/fastify` 2.x and `@modelcontextprotocol/node` 2.x, stateless, on a second fastify instance of awd (`daemon/src/mcp/`). It listens on `127.0.0.1:7433` by default, with the Host and Origin guards of the SDK. When the port is in use (for example, a second user on the same computer), awd takes the next free port up to 7442 and writes it to `~/.aw/run/mcp.port` (0600). `AW_MCP_PORT` selects one port, `0` (any free port: the tests) or `off`. The listener starts before the workspaces and the session managers (each window that the start opens finds the port file), and stops first. awd tries the port of the last run first (`~/.aw/run/mcp.port.last`). `aw-launch` reads that file and sets `AW_MCP_URL`; it always sets `AW_MCP_TOKEN`, also with MCP off, because the CLI and the hooks need the token. Only awd fails on a bad `AW_MCP_PORT`. `architecture.md` 6.4 is the design.
2. In front of the handler, awd compares the bearer token in constant time and maps it to {session, task, device}. The token (`awt_` and 32 random bytes) is in `~/.aw/sessions/<session>/mcp-token` (0600). awd mints it before the first window of the session, keeps it over each resume, and revokes it when the session record leaves `running` (stopped, moved, replaced, ended, failed). A missing, bad or revoked token gets HTTP 401 with no `WWW-Authenticate` header: Claude Code then reports the server as failed and starts no OAuth flow, because the server has a configured `Authorization` header. Tool handlers call the same service functions as the local API. A tool returns the error envelope of `architecture.md` 8 as a tool error (`isError`) and small, paged results (`thread`: at most `limit` events and about 60,000 characters per result, also for the parent threads). A running session whose workspace is not attached yet gets `not_ready`.
3. Plugin `.mcp.json` (Claude Code reads an `mcpServers` map at the plugin root): `{"mcpServers": {"aw": {"type": "http", "url": "${AW_MCP_URL:-http://aw-mcp-url-not-set.invalid/mcp}", "headers": {"Authorization": "Bearer ${AW_MCP_TOKEN:-none}"}}}}`. The defaults keep a session that AW did not start from sending the literal text, and its MCP calls fail with a host name that tells why.
4. Tool hints: `thread` and the resources are read-only. `ask`, `ready` and `artifact_add` are retry-safe, because Claude Code repeats a call once after a dropped connection: awd keeps the result of `ask` and `artifact_add` for 60 s by the session and the arguments; a repeated `ask` gets the same gate only while it is open, and the key of `artifact_add` holds the size and the time of the file. The server instructions stay under 4,096 characters. Tools: `thread`, `ask`, `message`, `stage`, `artifact_add`, `handoff`, `learn`, `approach`, `ready`, `task_create`, `gate`, `result`, `done`, `slot_acquire` (retry-safe) and `slot_release` (9.6.12). `ready` is retry-safe in the same way as `ask` (60 s by the session and the arguments). Resources: `aw://task`, `aw://knowledge`, `aw://knowledge/{+path}`.
5. The `aw` CLI exit codes are fixed: 0 ok, 1 refused or gate open, 2 invalid input, 3 awd not reachable. Hooks and scripts use the CLI only.

### 9.9 Orca session host
1. **Detect**: the Orca host reads `AW_ORCA`, then `/Applications/Orca.app/Contents/Resources/bin/orca` (macOS), then `orca-ide` or `orca` on PATH. It takes the first binary whose `--version` starts its first line with a version `x.y.z` (a prerelease suffix is ignored; on Linux, `orca` can be the screen reader). It checks `status --json` (runtime ready and reachable) and version 1.4.257 or later, and stores the full path. 1.4.257 is the version of the real test device; 1.4.268 was never tested with AW.
2. **Start**: AW makes the Orca worktree `aw-<key>` once (an older worktree `aw-<task-id>` or `aw-<created key>` of the task is found again): `repo add --path <checkout>` when Orca does not know the repo (else `worktree create` fails with `repo_not_found`), then `worktree create --name aw-<task-id> --repo id:<repo> --branch aw/<key> --no-parent --setup skip --json`. A branch that exists and is free is checked out as it is (`--base-branch aw/<key>`). A branch that is checked out in another folder gets a suffix in Orca (`aw/<key>-2`), and the task would then show a branch with no new commits: so a task keeps its branch and its folder when it changes host. A tmux session runs in the folder that has the branch, when AW made it for the task (`~/.aw/worktrees/<task-id>` or the Orca worktree `aw-<task-id>`). An Orca session for a branch that is checked out in `~/.aw/worktrees/<task-id>` runs in tmux there, with one comment; the Orca host refuses any other branch that is checked out (`branch_in_use`). `worktree create` opens a login shell, and AW closes it (`terminal close --worktree id:<id> --all`); when that close fails, the start fails, and the next start closes it first. AW reuses the Orca worktree `aw-<task-id>` only when git has `aw/<key>` checked out there (else a start error `branch_changed`). Then `terminal create --worktree path:<worktree> --title aw-<task-id> --command "exec env AW_NODE='<node>' AW_HOME='<home>' '<aw-launch>' <session>" --json`. `exec` replaces the login shell, so the pid from the result is aw-launch and then claude, and it leads its own process group. AW stores the pid, the handle, the worktree id and the `incarnationId`. `--command` is typed into a login shell, so it holds no token and no user text. aw-launch reads the launch file `~/.aw/sessions/<session>/launch.json` and `AW_HOME`, as in tmux: so the agent in Orca gets `AW_MCP_URL`, `AW_MCP_TOKEN` (from `run/mcp.port` and the token file) and `AW_CREDENTIALS_DIR` with no change to the command. A Done session (the work loop) stops and closes its Orca terminal through the Orca host.
3. **Input**: `terminal send --terminal <handle> --text <text> --enter --wait-submit 10 --json`, only after the SessionStart hook of the current terminal, and only when hooks report the agent idle (no UserPromptSubmit after the last Stop) and no permission request or dialog notification is open. Before the SessionStart, aw-launch runs or Claude Code loads, and Orca writes the text raw. Orca bracket-pastes the text for a known agent (`provider: claude`), so a multi-line answer stays one input; for another program it writes the text raw. After a failure whose error has `data.orchestrationRequestId` and whose code does not say "not sent" (`terminal_not_writable` too, as its reply asks), AW sends the same text again with `--retry-request <id>`. After a failure with no id (a time-out), AW sends again only after the retry wait, while the hooks say idle and no UserPromptSubmit confirmed the text. The text is an argument of the Orca CLI for the time of the call: the CLI has no stdin or file input, so a local user can read it with `ps` (exception in `engineering-rules.md` 12, approved by a maintainer for phase 1). AW adds no token of its own, but the text is what a person typed, so it can hold a secret. The Orca host refuses a text over 100 KiB (an event line is at most 64 KiB). One send has a time limit of 15 s (the wait of 10 s and 5 s for the CLI), because it runs in the check loop of awd.
4. **Output**: hooks and the transcript only, never `terminal read`. The trust screen has no hook, so AW pre-trusts the worktree (9.1); AW does not answer a trust screen in Orca. aw-launch pre-trusts only for a Claude Code version that the contract tests cover, so a session with another version runs in tmux (9.9.6). A terminal with no SessionStart after 120 s gets one comment that names the Orca worktree. An unknown dialog opens "Take over terminal" through the 15-min check of the watchdog (9.6.7): AW cannot see the dialog, so a turn with no hook event for 15 min opens the gate. The resume policy, the pauses, the stop of a revoked device and the stop at Done use the host of the session (tmux or Orca).
5. **State and stop**: `terminal show` gives the state: `connected: true` with the stored `incarnationId` is live; `connected: false` is dead, with `exitCause` `exited` (code) or `signaled` (signal). `terminal_handle_stale` means the terminal is gone. The forced stop of 9.7 runs on the stored pid only while Orca shows the stored incarnation, then `terminal close`. A stored handle with another incarnation is closed with no signal before a resume or at a stop. `terminal show` has a time limit of 5 s: it runs in the check loop of awd. After the signals, a failed `terminal close` is only logged: the session is stopped, and AW does not resume it. A stop keeps the Orca worktree, as tmux keeps `~/.aw/worktrees/<task-id>`.
6. **Choice**: "Use Orca on this device" is `use_orca` in `bindings.yaml` (default `false`). A checkout can set `session_host`. `task.created` and `task.assigned` can carry `session_host` (`aw task create|assign --host tmux|orca`, the local API `session_host`). The newest `task.assigned` or `task.created` that names a host wins (an assignment with no host keeps the host of an earlier event), then the checkout, then `use_orca`. When Orca is off or not available, or the contract tests do not cover the Claude Code version, the session runs in tmux and the task gets one comment with the cause. A running session keeps its host.
7. **Orca restart** (tested on Linux with a private Orca runtime, `orca-ide serve`, 1.4.257): the terminals live in the Orca terminal daemon, a separate process in its own systemd scope. A stop of the Orca runtime keeps the agent, the handle and the incarnation. While the runtime is down, each CLI call fails with `runtime_unavailable`; AW then neither resumes nor stops the session, and delivers the waiting texts after the restart. After 120 s with no answer, the task gets one comment "Orca does not answer on <device> since <time>", and one more when Orca answers again. `aw session stop` meanwhile gives 503 `not_ready`. A new assignment of the task meanwhile starts no new session (it could run in tmux in the same Orca worktree, next to the agent): the task gets one comment "The new session waits", and the new session starts after Orca answers and AW stops the old one. A kill of the terminal daemon stops the agent; Orca shows the terminal with `connected: false` and does not run the command again, so AW resumes the session in a new terminal.
