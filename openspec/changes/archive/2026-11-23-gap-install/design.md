## Context

Gap audit T2 (M5 to M10). awd already has the engine pins and `fetchEngine` (`plugins/sync-syncthing/src/pins.ts`), the service units (`daemon/src/units/units.ts`), the sign-in check of the agent (`ClaudeAdapter.authStatus`), the disk use (`continuity/processes.ts diskUse`) and the sync status of each peer. Node runs the TypeScript sources directly, and each workspace package exports `.ts` files. Node does not strip types in `node_modules`, so an npm package must hold JS. T1 (gap-setup) runs at the same time and changes `daemon/src/cli/run.ts`, `daemon/src/api/app.ts` and the desktop contract files, so this change keeps its edits there to registration lines.

## Goals / Non-Goals

**Goals:** one install path (`aw service install` places the engine and names a missing tmux), a headless Mac that reads its key, a capped awd log, a setup check with a fix for each failure, a JS npm package folder, a desktop packaging config, the Syncthing notices in each artifact.

**Non-Goals:** the release workflow and the publish (task release-pipeline), a signed app (task signing), the Homebrew cask, an engine inside the npm tarball, a notices list of the Kotlin libraries of the APK.

## Decisions

1. **The engine is fetched at install, not bundled in the npm package.** `aw engine install` uses `loadPins` and `fetchEngine` (sha256 check of the pinned archive) into the folder of `settings.sync.engine`. `--archive <file>` reads a local archive for an offline computer (same sha256 check). Reason: 4 platform binaries make a large tarball, and the audit scope says "fetches the pinned engine". `engineering-rules.md` release item 5 is changed to match. With `AW_SYNC_ENGINE` set, the command refuses: the person chose another binary.
2. **`aw service install` runs the engine install first.** A failed download prints a warning with the fix (`aw engine install` again, or `--archive`) and the unit install continues: awd runs with sync off and the setup check shows it. `--no-engine` skips the step. When the engine is new, the command restarts awd after the load (`launchctl kickstart -k`, `systemctl --user restart`), so awd starts the engine. Under `sudo` (LaunchDaemon) the engine folder is given to the user (chown).
3. **tmux check.** `hostBinary(settings)` finds tmux. When it is missing, the install prints `tmux is missing: AW sessions need it. Install it: <command>`. The command comes from the OS: `brew install tmux` on macOS; on Linux from `ID` and `ID_LIKE` of `/etc/os-release` (`apt`, `dnf`, `pacman`, `zypper`, `apk`), else a general text. The install continues.
4. **Headless keystore.** The LaunchDaemon plist sets `AW_KEYSTORE=file`. `--headless` refuses (exit 1) when `<AW_HOME>/identity.yaml` or `config.yaml` exists and `<AW_HOME>/keys/device` does not: then the key is in the login Keychain of the user, and root cannot read it. The message names the fix: `aw service move-keys` as the user, then the install again. `aw service move-keys` (a person command) refuses while awd answers on the socket, copies `device` and `master-phrase` from the OS keystore to the file keystore, reads them back, and then deletes the Keychain entries. The settings default is `file` when `<AW_HOME>/keys/device` exists, so a LaunchAgent or a terminal awd never makes a second key in the Keychain after a move.
5. **Log rotation by copy and truncate.** launchd keeps the log file open with `O_APPEND`, so a rename would not help. awd checks `<AW_HOME>/logs/awd.log` at start and every 5 minutes (clock module). Above 10 MB it moves `.2` to `.3`, `.1` to `.2`, copies the file to `.1` and truncates it to 0. Lines written between the copy and the truncate can be lost; this is accepted. systemd sends the log to the journal, so on Linux there is no file and the check does nothing.
6. **Setup check in awd.** `daemon/src/service/doctor.ts` has pure functions that turn probe results into checks `{id, title, status: ok|warn|fail|skip, detail, fix}`, and a probe set that awd fills (units, tmux, Orca when a binding asks for it, `claude --version` and `claude auth status --json` from the service context, `diskUse`, the clock, the sync state and peers, `pmset -g`, `fdesetup status`). The route is `GET /v1/doctor` with `config: { access: "person" }`. `aw doctor` calls the route; when awd is not reachable it runs the local probes (unit, tmux, engine binary, disk) and adds a failed `awd` check with the fix `aw service install`. Exit code 1 when a check failed.
7. **Clock check without new third parties.** Linux: `timedatectl show -p NTPSynchronized --value`. macOS: the `server` line of `/etc/ntp.conf` (the time server that the OS already uses), then `sntp -t 3 <server>` for the offset: warn above 5 s, fail above 60 s. No server line: warn, fix "turn on Set time and date automatically".
8. **macOS power checks.** `pmset -g`: `sleep` not 0 is a warning only with a LaunchDaemon (a laptop sleeps by design; the text names Sync before sleep). `autorestart` 0 is a warning; a missing line is `skip` (a laptop has none). FileVault on is a warning with a LaunchDaemon: after a restart the Mac waits for a login.
9. **npm package by tsc, with no bundler.** `daemon/scripts/build.ts` writes a temporary tsconfig (rootDir: the repository, `noCheck`, the list of shipped sources) and tsc emits each runtime source file of awd and of its workspace packages into `daemon/dist/npm/` in the same folder layout, so each `import.meta.url` path still works (`contracts/schemas`, `plugins/agent-claude/plugin`, `plugins/sync-syncthing/engine/engine.json`, `daemon/bin/aw-launch`). `daemon/scripts/build.ts` then rewrites each bare `@aw/<pkg>[/sub]` import to a relative path from the export map, writes a `package.json` with `type: module` in each package folder, copies the non-TS files, and writes the root `package.json` (bins, the third-party runtime dependencies of the closure with their exact versions, `engines`). The files that point at a sibling entry (`../bin/awd.ts`) use a helper that keeps the extension of the current module. `aw-launch` runs `aw-launch.js` when it exists. `--link-deps` links the third-party packages from the pnpm store into `<out>/node_modules`, so `task check` (`task daemon:package`) builds into `dist/npm-check/`, runs `aw --version` from it and removes it. Reason: `tech-stack.md` says "`tsc` builds awd and `aw`" and rejects tsdown for now. The package name is a constant (`agent-workspace`) until release-pipeline sets it.
10. **Desktop packaging.** `desktop/electron-builder.yaml` (the repository allows only `.yaml`; electron-builder gets `--config`): appId `com.agentworkspace.desktop`, `files: out/**`, `extraResources: THIRD_PARTY_NOTICES`, `mac.extendInfo.NSUserNotificationAlertStyle: alert`, `mac.hardenedRuntime`, `afterSign: scripts/notarize.mjs` (`build/` is in `.gitignore`). `scripts/notarize.mjs` returns at once unless the platform is macOS and `APPLE_API_KEY`, `APPLE_API_KEY_ID` and `APPLE_API_ISSUER` are set; then it calls `@electron/notarize`. electron-builder skips signing when no identity is found (`CSC_IDENTITY_AUTO_DISCOVERY` is not forced). A unit test reads the YAML and calls the hook with no variables.
11. **Notices.** Root `THIRD_PARTY_NOTICES` has the Syncthing section: the tag, the MPL-2.0 text, the source and AUTHORS links (no author list in the file: the leak check refuses email addresses). The APK copy is `android/app/src/main/res/raw/third_party_notices.txt`; the Devices screen opens it in a dialog. A test in `scripts/` checks that the copy is equal and that the tag equals the engine pins of the computers and of Android. The npm folder ships the root file. The desktop app ships `out/THIRD_PARTY_NOTICES`, which `desktop/scripts/notices.ts` writes at package time: the root file, then each JavaScript package of the bundle with its license text (`pnpm licenses list --prod --json`). This list is not committed: license texts have email addresses, which the leak check refuses.
12. **Desktop Setup check page.** Route `settings/setup`, linked from Settings. It calls `doctor` through the bridge, lists each check with its status and fix, and shows the Claude sign-in step and the AGT-14 text. A "Check again" button runs the call again.

13. **Lockfile deprecation text in the leak check.** electron-builder pulls glob 7, and pnpm copies its deprecation text, with the contact address of that public package, into `pnpm-lock.yaml`. The leak check skips only the `deprecated:` lines of `pnpm-lock.yaml` (with a test); each other line of the lockfile is still checked.
14. **Build script allowlist.** `electron-winstaller` (a dependency of electron-builder) has a build script for the Windows installer. `pnpm-workspace.yaml` lists it with `false`: it installs, its script does not run.

## Risks / Trade-offs

- [The npm folder is not tested with a real `npm install`] → `task check` runs `aw --version` with linked dependencies; the real install is in "Test later".
- [electron-builder is not run in `task check` (slow, downloads Electron)] → the config test checks the keys; the package run is in "Test later".
- [Copy and truncate can lose a few log lines] → only at 10 MB, every 5 minutes at most.
- [`sntp` reaches the time server] → it is the server that the OS already uses, and only when the person runs the check.
