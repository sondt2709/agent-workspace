## Context

- awd makes `config.yaml` with a device from the host name (awd-api-cli decision 2). Sync peers are in `<AW_HOME>/sync-peers.json`, and `aw sync peer add` shares each folder with any device id behind `AW_SYNC_TEST_PEERS` (sync-syncthing decision 18).
- `device.v1` exists with keys, sync device id, `seq`, `revoked` and `signature`, but nothing signs or checks it (data-model open issue 4). The merge applies events of a revoked device (merge-index open issue 4).
- The layout has `devices/<device>/device.yaml` (writer: a device with the master key), `devices/<device>/sealed/<id>.age`, `secure/credentials/<name>.age`. No code writes them.
- The knowledge store has `setSecrets()`, and the files layer has `setSecrets()`. No caller gives them credential values (knowledge open issue 5).
- A parallel task (sessions-tmux) changes `daemon/`. So the new code is in new files, with one wiring point in each shared file.

## Goals / Non-Goals

**Goals:**
- A device key on each device, the master key with a recovery phrase on the local device, signed device records, a check of each record, revoke.
- Pairing of a computer with one code: `aw device add` on the local device, `aw pair <code>` on the new device, the check code, `aw device approve`. The pairing API for the apps.
- The workspace credential key, credential files, `aw credential`, the import of a phone credential file, the secrets for the redaction.

**Non-Goals:**
- The desktop and Android pairing screens (desktop-devices-kb, android-engine, android-ui use the API).
- Session injection of credentials (task-loop uses `aw credential get`).
- Pairing of a phone end to end: the phone side does not exist. The computer side of the phone outbox is built and tested with a simulated phone file. Sealing the master key to a phone is not built.
- Restore from the recovery phrase on a new local device, and a reset of the identity.
- The check of signatures in the Kotlin merge (android-engine adds Tink).

## Decisions

1. **New package `shared/identity` (`@aw/identity`)** for the crypto, the record format, the pairing code and the keystore. The desktop main process needs the same code later. Alternative: a folder in `shared/core`; rejected, because core has no crypto dependency and the phone ports only the merge.
2. **Master key = a 24-word BIP-39 phrase** (`@scure/bip39`, English list, 256-bit entropy). The Ed25519 secret is HKDF-SHA256 of the BIP-39 seed (salt `aw-master-key-v1`, 32 bytes). awd stores only the phrase in the keystore (`master-phrase`). The user id is `u` + the lowercase base32 of the first 16 bytes of SHA-256 of the master public key. Alternative: a random key with a separate phrase encoding; rejected, the phrase is the key (architecture 4.1.1).
3. **Device key** = a random Ed25519 secret and an age X25519 identity (`AGE-SECRET-KEY-1…`) in one keystore entry `device` (JSON). The record has the raw public keys in base64; `@scure/base` bech32 converts the X25519 key to an age recipient `age1…`.
4. **Keystore** `AW_KEYSTORE`: `os` (macOS Keychain or the platform store, `@napi-rs/keyring`) or `file` (`<AW_HOME>/keys/<name>`, 0600 in a 0700 folder). The default is `os` on macOS with the default state folder `~/.aw`, else `file`: a headless Linux computer has no session bus (architecture 4.1.2), and a state folder from `AW_HOME` (tests, Docker, a second awd) must not write into the Keychain of the user. The OS entry account name holds a hash of `AW_HOME`, so 2 state folders never share a key. Tests and Docker use `file`.
5. **The master key is made by the first `aw workspace init` of a new workspace on a device with no identity.** That device is the local device. A device that registers an existing folder or joins by pairing never makes a master key. Alternative: make it at the first start; rejected, a new remote device would get its own identity before `aw pair`.
6. **Record signature**: Ed25519 over `aw-device-record-v1\n` + canonical JSON (sorted keys, no spaces) of the record as written in the YAML file, without `signature`. The check reads the raw YAML value, not the zod value, so a default of a newer minor version does not change the signed bytes. The writer writes each field explicitly.
7. **Record check in the merge**: `MergeEngine` gets an optional `verifyDeviceRecord(raw)`. A record that fails gets the issue `bad_document` with the reason `bad_signature` and keeps the last valid record (the "Last valid document" rule). A valid record with a lower `seq` than the kept record gets the reason `old_sequence` and is not used. awd gives the check only when it knows the master public key; an unpaired device keeps the current behavior. The Kotlin merge has no check yet (non-goal).
8. **Revoke cut-off**: the revoke record has `revoked_at`, the HLC of the master device at the revoke. The task fold and the workspace fold do not apply an event of a revoked device whose HLC sorts after `revoked_at`; the reason is `device_revoked`. A change of a device record folds each task and the workspace again. Heartbeats stay: the device view shows `revoked: true`. Alternative: ignore each event of a revoked device; rejected, the work before the revoke must stay (principle 9). Risk: a revoked device can write events with an old HLC (see Risks).
9. **Peers from the records**: awd computes the peers from the valid, not revoked records of each open workspace and of the pairing cache `<AW_HOME>/records/<workspace>.json` (the records that the pairing reply gave, before the `tasks` folder syncs). The highest `seq` wins. `SyncthingTransport` gets `persistPeers: false` and `setPeers(records)`, which adds and removes devices. The test path `POST /v1/sync/peers` adds a peer in memory only, still behind `AW_SYNC_TEST_PEERS`. The peer addresses are the record `addresses` and `dynamic`.
10. **Pairing protocol** (`docs/phase-1.md` 7):
    1. The showing awd (needs the master key) makes a nonce (16 bytes, hex, so the pairing id never starts with `-`), a secret (32 bytes) and an expiry (10 min). The code is `aw1:` + base64url of the JSON offer: user id, master public key, workspace id and name, showing device slug, Ed25519 key, sync device id, addresses, nonce, secret, expiry.
    2. The new awd decodes the code, refuses an expired code, adds the showing device to its engine (no workspace folder), and shares the folder `aw-pair-<nonce>` (`<AW_HOME>/pairing/<nonce>/`) with `request.json`: slug, name, role, keys, sync device id, addresses and an HMAC-SHA256 with the secret.
    3. While a pairing is open, the showing awd reads the pending devices and folders of the engine every 1 s (`GET /rest/cluster/pending/devices`, `/folders`). It adds a pending device with no folder, then accepts only the folder `aw-pair-<nonce>` of the open pairing. It checks the HMAC of the request. The first valid request uses the code: a second request is refused.
    4. Both sides show the check code: 6 digits from SHA-256 of `aw-check-v2\n` + canonical JSON of the Ed25519 key and sync device id of the showing device and of each field of the request without its HMAC (nonce, slug, name, role, both keys, sync device id, addresses). The human so checks each value that the approval signs, seals to and shares with.
    5. `aw device approve <pairing> <check code>` (the human types the code from the new device) signs the record of the new device (`seq` 1), writes it, seals the credential key to it (a computer), copies the knowledge history store into `history/` of the pairing folder (not `seen.json`), writes `response.json` with the signed records of both devices, and adds the new peer (`setPeers`).
    6. The new awd checks each record with the master public key of the code and that its own record has its keys and sync device id. It saves the user id and the master public key in `identity.yaml`, the role and slug in `config.yaml`, the records in the pairing cache, and the history in `<AW_HOME>/history/<workspace>/`. It adds the workspace folders at `--path` (default `~/AW/<workspace name>`), waits for `tasks/workspace.yaml`, registers the workspace and writes `done.json`.
    7. Both sides remove the pairing folder and the device of a failed pairing. An awd restart ends an open pairing.
11. **Pairing API is asynchronous**: `POST` starts or joins and returns an id and the state; `GET /v1/pairing/{id}` gives the state (`waiting`, `check`, `approved`, `joining`, `done`, `failed`, `expired`, `cancelled`). `aw device add`, `aw pair` poll it. A long-held HTTP request was rejected: the apps need the check code while the pairing waits.
12. **Join rules**: the new device refuses a code when it has a master key or other registered workspaces with a different slug; its role is `remote` (a computer); its slug is the current slug, or `--slug` when no workspace is registered. The showing device refuses a slug that a valid record has already.
13. **Credential key** = one age X25519 identity per workspace. `secure/keys/<device>.age` is that identity sealed to the device recipient of each computer (a new layout rule, writer: shared, computers only). `secure/credentials/<name>.age` is the value sealed to the credential key. A value from stdin or `--file` loses one trailing newline.
14. **Phone outbox**: `devices/<phone>/sealed/<id>.age` is the age file of `{"kind":"sealed-credential","v":1,"name","value"}` to the device recipient of each computer. A computer with the credential key imports a file of a device whose valid record has the role `mobile`, when no `credential.imported` with that `sealed` id is merged. It writes `secure/credentials/<name>.age` and `credential.imported {name, from, sealed}`. awd checks the outbox every 10 s and after each merge change. The phone removes its file (phone side).
15. **Secrets for the redaction**: at the workspace open and after each credential change, awd opens each credential and calls `setSecrets` of the files layer (each event line) and of the knowledge store. Values stay in memory only.
16. **Rotation at revoke**: the revoke makes a new credential key, writes each credential again with it and seals it to each remaining computer. The sealed file of the revoked device keeps the old key: the revoked device had it already, and a delete would need another delete in the files layer.
17. **`aw credential get <name>`** prints the value to stdout for the session start of task-loop. It is a human command; the session token rule of follow-up 5 must refuse it for an agent.
18. **QR**: `qr` 0.7 in daemon. The pairing reply has `qr_svg`; `aw device add --qr` prints the ASCII form.
19. **`config.yaml` keeps the device** (slug, name, role) as the local copy of the identity. Pairing sets the slug and the role. On a device without the master key, an own valid record with another name or role corrects `config.yaml` (the slug changes only by pairing, because the open workspace services use it). Alternative: move the device to `identity.yaml`; rejected, it changes each test helper and the sessions-tmux code at the same time.
20. **Review fixes (before merge)**: the credential key cache compares the sealed bytes on each use, so a rotation from another computer needs no restart, and a credential that does not open for a time keeps its last value for the redaction. A revoke is final in the merge (`revoke_removed`, and `old_sequence` for a record without the revoke), and the device with the master key writes the newest record again when the file on disk is missing, refused or older. The pairing response has the newest record of each device, revoked ones too; approve refuses a revoked slug, key or sync device id, runs one at a time, checks the credential key before the record write, and writes the record once per pairing. Peers compare `seq` only inside one workspace, and a revoke in one workspace removes the peer. The show side accepts the pairing folder from a peer too (a second workspace). `aw pair --path` is absolute; the default folder name has no separator. awd gives the identity to open workspaces as functions (`hasMasterKey`, `verifyDeviceRecord`), so `createMaster()` and `adopt()` apply at once.
21. **Review fixes, round 2 (before merge)**: the check code covers the full request (an attacker with a leaked code and the public Ed25519 key of the new device cannot put in its own X25519 key or sync device id). The workspace id of a code and of a response is a UUIDv7, and the pairing cache refuses any other id, because the new device uses it in paths. The nonce is hex. `aw device approve` takes the code with or without the space; `aw pair -` reads the code from stdin. A second join with the same code while the first runs is 409 `conflict`; a retry of the last join step does not register again. The showing device refuses a device that wrote no request 60 s after its folder was accepted, and a refused device can offer again. The phone outbox import checks the file id and the credential name before it writes, and one bad file never stops the others. The rotation keeps the old keys of this process in memory: the device with the master key writes a credential that only an old key opens again with the current key, and the revoke reply names the credentials that no key opened (`closed`). The import delay reads the clock module.

22. **Review fixes, round 3 (before merge)**: `aw pair` refuses a folder with `tasks/workspace.yaml` of another workspace or with other files (409), and the join step checks the id of `tasks/workspace.yaml` before it registers the folder; a wrong id removes the folders from the engine and fails the pairing. A workspace has one open pairing (409 for a second one, decision 14). While approve runs, the code does not expire and a cancel is 409; approve stops when the pairing ended during one of its steps. The request has an Ed25519 signature of the device key (`sig`; the HMAC covers it, the check code does not), so a code holder cannot ask for the record of a known device with its public key; approve also refuses a request with the slug, key or sync device id of the showing device. A join whose engine calls fail ends as `failed`, so the same code works again. A revoke on a device that cannot open its own credential key names each credential file in `closed`. The history copy uses `COPYFILE_EXCL`. Accepted risk: the check code covers fields that the requester chooses, with no commitment, so an attacker with a leaked code who can see the real check code can try about 1,000,000 requests to get the same code and must still send its request first (the code is valid for 10 minutes and used once). A commitment step is a later change if the risk grows.

## Risks / Trade-offs

- [A revoked device writes events with an HLC before `revoked_at`] → Those events merge. The cut-off is the only rule that each device computes the same way; the human sees the events in the thread. Recorded as an open issue.
- [Any device can connect while a pairing is open] → awd adds a pending device with no workspace folder and accepts only the folder of the nonce; the HMAC, the single use and the check code decide. Devices of a failed pairing are removed.
- [All workspaces of a computer share one peer list] → All workspaces of one awd belong to one person (one master key). A pairing of one workspace shares the folders of each workspace with that device. Open issue for more workspaces.
- [The recovery phrase is shown by `aw identity phrase` over the local socket] → The socket is 0600; follow-up 5 (session callers) must refuse it for agents.
- [Keychain prompts on macOS] → Tests use `file`; one opt-in test (`AW_E2E_KEYCHAIN=1`) runs the real Keychain.
- [The pairing folder carries the history store] → It holds the same knowledge versions that the `knowledge` folder syncs; it never holds a key. The credential key goes sealed in `secure/`.

## Migration Plan

No release exists. A state folder of an earlier build keeps `config.yaml`; its `sync-peers.json` is not read. A state folder of an earlier build that has workspaces and no identity gets no master key (only a new `aw workspace init` makes one), so it cannot show a pairing code: make such a dev or test state folder again (a new `AW_HOME` and `aw workspace init`). Rollback: revert the commit.
